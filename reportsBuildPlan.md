## S1.2 `ReportPage` (abstract)

- `use HasFiltersForm, InteractsWithTable, HasReportFilters, HasReportTable, HasReportBanner, HandlesActionExceptions;` implements `HasTable`. `#[On('calendar-toggled')] calendarToggled(): void {}` (project base-page rule, filamentPattern §1.19). `protected string $view = 'filament.pages.reports.report'`.
- `abstract protected const PERMISSION` (e.g. `view_customs`); `abstract protected static function service(): string` (service class); `abstract public function filtersForm(Schema $schema): Schema` (composes `HasReportFilters` fields); `abstract public function table(Table $table): Table`; `protected function getHeaderWidgets(): array` (charts, with `WidgetConfiguration` where needed); `protected function getFooterWidgets(): array` → `[static::ATTENTION_WIDGET]`.
- Authorization: `public static function canAccess(): bool { return auth()->user()?->can('report.'.static::PERMISSION) ?? false; }` (gates navigation + mount, Filament 403). Widgets: `public static function canView(): bool` on each widget subclass checks the same string via `const REPORT`.
- Cards: `#[Computed] public function summary(): array` → `service::summary(ReportFilters)`; rendered in the shared blade with `<x-filament::section>` grid (no widget classes for cards — minimal). Charts/attention are widgets because they need Chart.js / a second table.
- Filters → service: `ReportFilters::fromArray($this->filters ?? [])` everywhere; `updatedFilters()` additionally calls `$this->resetTable()` and `$this->dispatch('report-filters-changed')`. Widgets re-render through `#[Reactive] $pageFilters` (F3).
- `getNavigationGroup()` → `__('resources/dashboard/strings.navigation_group.reports')`; `getTitle()`/`getNavigationLabel()` → `resources/report/strings.pages.{key}.title`; `$navigationSort` = spec number.
- Rows are never `$record->toArray()` dumps: each service exposes `query(ReportFilters): Builder` (main table), `summary(ReportFilters): array`, `chart{Name}(ReportFilters): array`, `rows(ReportFilters): iterable` (export, same column whitelist as the table).

## S1.2b Architecture and page design standard (owner-settled 2026-10-19/20; supersedes any older layout wording above; applies to EVERY report)

**Architecture (folders).** Services: `app/Services/Reports/{Builders,Rules,Checks,Support}` — `Builders/` holds the `ReportService` contract and one `{Name}ReportService` per report (query / summary / rows / exportLabels / chart data); `Rules/` the shared `FxRateService`, `ShipmentCurrencyResolver`, `ReportStages`; `Checks/` the `Check` DTO, `CheckRegistry` and one `{Model}Checks` per model; `Support/` `ReportFilters` and `ReportCsvWriter`. Every widget is appended to `DashboardPanelProvider::widgets()`. Tests: two masters per report (`{Name}ReportTest` in Services = builder + checks, `{Name}ReportPageTest` in Filament = page + widgets) plus the shared `ReportsEngineTest` and `ReportPageBaseTest`.

**Page, top to bottom (one shared view `report.blade.php`):**
1. **Filters** — ONE full-width accordion headed «Filters» (funnel icon), COLLAPSED by default, opened on demand; fields in a grid of 1 column on mobile, 2 on tablet, 4 on desktop; every dropdown lists ALL active master rows (used or not), names in Farsi under `fa` and English otherwise; changing any filter refreshes cards, charts, table and the issues accordion together; filters live in the URL so a link reproduces a view.
1b. **Guide** — ONE collapsed accordion «How to read this report», the FIRST element of the page (above the Filters bar), whose five sections are TABS (Filters / Cards / Charts / Table / Data issues) instead of nested accordions; the tab bar and the selected tab's content (info blocks in a 2-column grid on wide screens) sit together in a NESTED inner card inside the accordion (shared view `guide.blade.php`, content from `lang/{en,fa,fr}/resources/report/guide_{key}.php`): an `intro`, then collapsible sections `filters`, `cards`, `charts`, `table`, `issues`, each with `title`, optional `intro` and `items` keyed by name (filter field state name, card key, short chart name, table column name, check key with the dot replaced by an underscore); every item has `title`, `meaning` (what it represents), `how` (how the number or flag is produced, exact rule in plain words incl. thresholds, fallbacks and exclusions) and `change` (what to change to see different results; for a data issue, which form field to edit). Written in plain non-technical sentences, native Persian and French, reusing the app's own labels. Content rules (owner, 2026-10-20): verified against the code AND cross-checked with the plan documents, but the documents are never cited in the text — they are used to cover the reader's blind spots (what the report does not include or cannot know, owner-decided definitions and why, production realities such as empty status history / no usable FX rate / empty dates, filters that narrow only part of the page); no filler, no vague or circular sentences, no invented rules; omit a part (`meaning`/`how`/`change`) rather than pad it. It is mandatory for every report, and the report's page test MUST assert completeness (all five sections in en/fa/fr, an item for every filter field, card, chart, table column and every check returned by `forReport()`, none empty).
2a. **Clickable stat lines (owner, 2026-10-20)** — every card line that is a SET OF TABLE ROWS carries a `quick` key (snake_case; ids inside the key, e.g. `queued_currency_12`); a click calls `ReportPage::filterTableBy()`, sets `?q=`, highlights the line, shows the chip «Table filtered by: card — line» with «Show all rows», and the builder's `query()` narrows the table to EXACTLY the records the line counts. The card/filter predicate is ONE shared private method per line so they cannot drift. Lines that are not row sets (euro totals, «excluded», averages, lines counting other entities such as correspondences) are NOT clickable. `quick` never reaches cards, charts, checks or their caches (`cacheKey()` ignores it); the CSV export follows it. A line whose card ignores the table's default open/closed restriction must widen the table base for its own key. Each report proves the invariant «line value == filtered row count» in its builder master and the click/URL/chip behaviour in its page master.
2. **Stat cards** — exactly four, laid out 4 in one row on desktop and 2 per row (2 + 2) on mobile; each card is a heading plus label/value lines; money is one line per currency (never summed across currencies) followed by a euro-total line from `FxRateService`, and an «Excluded (no rate)» line naming any currency without a Purchased/Received rate (strict, never guessed); averages show «-» when there is no data.
3. **Analytics** — the charts, in a 2-column grid directly under the cards and ABOVE the table, rendered by `ReportPage::analytics()` from the page's `analyticsWidgets()` (not as header widgets, which would sit above the filters).
4. **Main table** — one row per record, striped, 10/25/50/100 per page, default sort on the most urgent column, toggleable columns (the heavy ones hidden by default), a «CSV export» header action that queues `ExportReport`.
5. **Issues accordion (the data-check log)** — ONE accordion, COLLAPSED by default, headed «N open data issues», shown ONLY when the filtered report has at least one issue (a clean report shows nothing, never an empty table). Inside: first the severity chips «Error: n», «Warning: n», «Info: n» (a chip is hidden at zero) and «Show all»; clicking a chip dispatches the Livewire event `report-severity` and the attention table below filters to that severity (it only evaluates the checks of that severity); then a divider and breathing space, then the attention table. The info line «some records have no status history yet, their age counts from the last edit» appears under the chips when notes exist.

**The attention table (log) in detail.** Columns: record (identifier, linked to the edit page only when the viewer may edit), problem, current value, expected value, severity badge (Error red, Warning amber, Info blue), changed by, changed at (adaptive Jalali/Gregorian date-time; «-» when unknown). Two table filters: severity and check. Rows are sorted errors first, then by record label; 10/25/50 per page; empty state is the app's standard. Data comes from `CheckRegistry`: ONE offender query plus ONE batched who/when query per check (latest `audit` activity row, or the `status_histories` user for status fields), cached 5 minutes per (check, filters, user, locale) and flushed by `ReportCheckObserver` on every save/delete/restore of a checked model (and the FX rate cache with it). A check never blocks a save; a record with NO status stays listed by the open-payment checks and is flagged by `status_missing`. Production fallbacks stay visible, not hidden: days-in-status falls back to `updated_at` while `status_histories` is empty and is flagged.

**Behaviour rules.** Reuse before adding (existing lang keys, bank-profile/shipment resource columns and enums); all user-facing text in en/fa/fr with real Persian and French; zero code comments; the widget gate `canView()` mirrors the page permission `report.view_*`; the app must boot (`php artisan about`) after every new Filament class because one fatal takes the whole panel down.

## S1.4 `FxRateService` (EUR base; reportsPlan rule)

```php
public function eurCurrencyId(): ?int                // currencies.english_name = FxRateService::EUR_NAME ('Euro'; verified against production: one active row, id 2; no 'EUR' key exists)
public function rate(int $from, int $to): ?array     // ['rate'=>float,'bank_profile_id'=>int,'date'=>?Carbon]
public function toEur(float|string|null $amount, ?int $currencyId): ?float   // null when no rate; same currency → 1
```
- Candidate profiles: `bank_profiles` not trashed, `status_id` ∈ ids of `Status::findBy(BankProfile::TYPE_BANK_PROFILE, 'Purchased'|'Received')`, `requested_amount > 0`, `purchased_equivalent > 0`, both currency ids set. Direction A (`requested_currency_id=from`, `purchased_currency_id=to`): `rate = purchased_equivalent / requested_amount`. Direction B (swapped): `rate = requested_amount / purchased_equivalent`. Pick latest by `purchase_date DESC NULLS LAST, id DESC` across both directions.
- Caching: per-request static memo + `Cache::remember("reports:fx:{version}:{from}:{to}", 300)` (a missing pair is cached as a sentinel) (cross-model aggregate → plain cache, same reasoning as AnalyticsService). `FxRateService::flush()` for tests.
- A null rate never silently drops: the caller records `fx_rate_missing` in the banner and shows "excluded: X {CUR}" beside the EUR total.
- Explicitly NOT `bank_profiles.exchange_rate` (Rial rate per owner fact) and not `conversion_rate`/`final_rate`.

## S1.8 Performance rules (up front)

- Every service method is one SQL statement or a `leftJoinSub` composition (per-RO aggregates: bank profiles sum, shipments count, customs resolved value, last activity) — never per-row relation calls in a table column; table columns read pre-aggregated select aliases.
- Eager loads declared once in `query()` (`with([...])`), status rows resolved once per request (`Status::findBy` memo in `ReportStages`), FX rates memoised.
- Indexes to add in the same migration (cheap, evidence-backed by the queries below): `bank_profiles(status_id, deleted_at)`, `bank_profiles(commitment_payment_date)`, `customs(clearance_status_id, deleted_at)`, `shipments(shipment_status_id, deleted_at)`, `shipment_items(product_id)` (FK index), `shipment_items(shipment_id)` (FK index).
- Percentile-based outlier checks: SQL `ORDER BY value`, PHP index pick (AnalyticsService precedent).
- Month charts (R5, R6): bucket in PHP (`jdate()->format('Y-m')` when `isJalaliCalendar()`, else Gregorian) — datasets are tiny (≤ few hundred rows), Jalali months do not align with Gregorian SQL buckets.
