# BMS-CM Livewire Pattern

Two kinds of component live under `app/Livewire/`:

| Component | View (`resources/views/livewire/…`) | Role |
|---|---|---|
| `CalendarToggle` | `calendar-toggle.blade.php` | Topbar Gregorian↔Jalali toggle, session-backed (`calendar_type`), dispatches `calendar-toggled` |
| `TableStateToggle` | `table-state-toggle.blade.php` | Topbar "remember my table setup" toggle, session-backed (`persist_table_state`), dispatches `table-state-toggled` |
| `RowClickToggle` | `row-click-toggle.blade.php` | Topbar "clicking a row opens Edit" toggle, session-backed (`row_click_edit`), dispatches `row-click-toggled` — Operational resources only, see its own consumer-wiring entry below |
| `LandingPage\{Workflow, Workspace, Search, Features}` | `landing-page/*.blade.php` | Landing-page tab bodies — see `viewsPattern.md`, eager render-only, no Livewire reactivity |

## The topbar-toggle pattern (CalendarToggle → TableStateToggle → RowClickToggle mirror family)

A **session-backed** preference that must influence **server-side rendering** (calendar pickers, table config) cannot live in `localStorage` — the server never reads the browser's storage. Both topbar toggles of this kind follow one shape, and a new one should copy it:

1. **Component** — `mount()` seeds a public bool prop from `session('key', default)`, `toggle()` flips the prop, writes `session([...])`, and `$this->dispatch('<thing>-toggled')` (the event name is the contract other classes listen for).
2. **View** — a single `<x-icon-button wire:click="toggle">` with the tooltip baked in PHP (`@php` block picks the state-appropriate `__()` string — server round-trip makes it reliable by construction, per scriptPattern §10's tooltip lesson). State shows as icon recolor (`text-primary-600 dark:text-primary-400`), not a second button variant — the two-static-variant `x-show` shape is only needed for client-only toggles where no server round-trip exists.
3. **Topbar wrapper** — a one-line `resources/views/filament/partials/{name}-toggle.blade.php` containing `@livewire('{name}')` (NOT a `@include` of the view directly), registered at `GLOBAL_SEARCH_AFTER` in `app/Configurators/FilamentRenderHooks.php`, with an inline `style="order: N"` on the view's root div (see stylesPattern's `.fi-topbar-end` order table for taken slots).

**Event consumers differ by what re-renders:** `calendar-toggled` has real `#[On]` listeners — every `App\Filament\Pages\*` base class implements `calendarToggled()` (no-op soft re-render on List/Manage, a `redirect(Referer)` on Create/Edit because the jalali picker is `wire:ignore`'d — filamentPattern §1.19). `table-state-toggled` deliberately has **no listener**: `FilamentTableDefaults`' `->persistInSession(fn () => session('persist_table_state'))` condition is lazily re-evaluated on every table render, so the next Livewire interaction picks the flag up on its own — adding a redirect-style listener would force a pointless reload.

**Known footgun (do not re-trip):** a topbar render hook is fine for a tiny self-contained toggle component, but do NOT embed page-like Livewire content there expecting page-component behavior — a prior topbar Desk-Reference dropdown attempt rendered correct server HTML yet never appeared client-side, root cause never isolated (`viewsPattern.md` "Dead-code sweeps"). Header Action + modal (see `HasDeskReferenceAction`) is the working equivalent.

**Consumer wiring for `persist_table_state`:** `app/Configurators/FilamentTableDefaults.php`'s `Table::configureUsing(...)` sets `->persistInSession(fn (): bool => (bool) session('persist_table_state', false))` on every table in the panel — default OFF (opt-in), one shared lever, no per-resource wiring. Filament then persists filters/search/sort/columns/grouping/records-per-page to its own session keys automatically.

**Consumer wiring for `row_click_edit` is NOT `Table::configureUsing(...)` — that point is too early.** Vendor `Filament\Resources\Pages\ListRecords::makeTable()` (and `InteractsWithRelationshipTable` for RelationManagers) always calls `static::getResource()::configureTable($table)` — which runs each resource's own `table()` method, including its `->recordUrl(null)` — INSIDE `makeTable()`, before it returns. A `Table::configureUsing()` default is set at `Table::make()` construction time, earlier still, so both the vendor fallback AND the resource's own customization overwrite it unconditionally; it silently has zero effect (confirmed via a failing test on a first attempt, 2026-10-05). The correct override point is this project's own `App\Filament\Pages\ListRecords::makeTable()`, which chains ONTO the return value of `parent::makeTable()` (i.e. after everything above has already run) — see `filamentPattern.md`'s row-click-to-edit entry for the exact method body. Because every Operational resource's List page extends this class and Master Data's `ManageXxx` pages extend the sibling, untouched `App\Filament\Pages\ManageRecords`, the feature is Operational-only by construction, no model allowlist needed. `recordUrl()`, never `recordAction()` — the latter renders each cell as a `wire:click`-bound `<button>` sharing a `wire:target`/`wire:loading` channel with the row's own actions-dropdown buttons (same method name, `mountTableAction`), which can disable the entire dropdown; `recordUrl()` renders a plain `<a href>` with no Livewire wiring at all, structurally immune to that class of bug. A `#[On('row-click-toggled')]` empty listener on `ListRecords` (mirroring `calendarToggled()`) is required so an already-open list page repaints when the topbar toggle flips.
