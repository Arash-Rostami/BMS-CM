# Reports services

## Layout (one folder per kind, one folder per report on the screen side)

```
app/Services/Reports/
    Builders/   ReportService (the contract) + one {Name}ReportService per report (query / summary / rows / exportLabels / chart data)
    Rules/      FxRateService, ShipmentCurrencyResolver, ReportStages, RequesterStages (shared money and status rules)
    Checks/     Check, CheckRegistry, {Model}Checks (BankProfile, RegisteredOrder, Shipment, Custom, Correspondence) + one file per report that owns checks (InTransit, Executive, Requester, FxCommitment)
    Support/    ReportFilters, ReportDates, SqlToday, ReportCsvWriter, FileActivity, FileRowLoader, ActivityFeed (R2), RequesterRowLoader (R7), TransitLedger (R1), FxCommitmentLedger (R6)
app/Filament/Pages/Reports/
    ReportPage.php + Concerns/        shared page base and field/table/banner helpers
    Widgets/ReportAttentionWidget     shared widget base
    {FxSupply,Operations,Customs,InTransit,Requester,Executive,FxCommitments}/   one folder per report: the page, its charts, its attention widget
```

Seven reports, keys / permissions (`report.view_{key}`) / nav sort: `executive` 1, `operations` 2, `fx_supply` 3, `in_transit` 4, `customs` 5, `fx_commitments` 6, `requester` 7. Chart rule (owner): never two bar charts in one report; stage shares are doughnuts, month trends lines, comparisons bars. Types today: R1 stacked bar (value by category) + doughnut (EUR by ETA bucket); R2 doughnut (stages) + stacked bar (idle by stage) + the activity-feed table widget; R3 doughnut (funnel) + grouped bar (queued by bank); R4 doughnut (tracking stages) + stacked bar (ETA buckets); R5 bar (stage) + line (clearance days by month); R6 line (remaining by month) + horizontal bar (by bank); R7 doughnut (stages) + stacked bar (late by stage). `ReportPageBaseTest` discovers every chart widget under `Pages/Reports` from the panel's widget list and renders each with empty and unfiltered data.

**In-app guide.** `ReportPage::guide()` (computed) reads `lang/{en,fa,fr}/resources/report/guide_{key}.php` — `intro` plus `sections` (`filters`, `cards`, `charts`, `table`, `issues`; each with `title`, optional `intro`, `items` keyed by filter field name / card key / chart name / table column name / check key with `.` → `_`; each item `title`, `meaning`, `how`, `change`) — and `resources/views/filament/pages/reports/guide.blade.php` renders it at the very top of the page (above the Filters bar) as ONE collapsed accordion card (icon, title, the report intro as its description) holding a NESTED inner card with the five section TABS (each with an icon) and the selected tab's content as a responsive grid of info blocks (title + meaning / how / change rows, each row with its own icon); no nested accordions (labels in `resources/report/strings.guide.*`); a report without a guide file simply shows none. Every report's page master pins the guide's completeness in all three locales.

**Clickable stat lines.** `ReportFilters::$quick` (token; in `toArray()`, NOT in `cacheKey()`), `ReportPage::$quick` (URL `?q=`), `ReportPage::filterTableBy($key)` (toggle, validates the token), `ReportPage::quickLabel()` and the view (clickable row + highlight) let a summary line carrying `'quick' => key` filter the main table; the active line shows as the table's NATIVE filter indicator (`HasReportTable::quickFilter()` = `Filter::make('quick')->indicateUsing(...)`; `ReportPage::removeTableFilter()` clears `quick`, so the native remove / «remove all» works). Only the table query (and the CSV export built from it) reads `quick` — cards, charts, checks and the issues log never do. Changing any filter clears `quick`; a stale or foreign key (shared URL) still shows the indicator, so the narrowed table can always be reset. A line may also carry `url` (drill-down link to another report page, rendered beside the label). The «Reset filters» action is a table header action next to the CSV export (`HasReportTable::resetFiltersAction()`, visible only when a filter or `quick` is active; `ReportPage::resetReportFilters()` refills the form and clears the severity chip). A calendar switch redirects the page to the previous URL (`calendarToggled()`), so pickers, charts, checks and the feed all re-render in the new calendar; filters survive in the URL/session. `ExportReport` authenticates its user and sets the dispatched calendar only for the duration of the job and restores the previous user and calendar afterwards, so a long-running worker never leaks them into later jobs. The `ReportService::summary()` docblock is the contract.

A new report adds one builder in `Builders/`, its checks in `Checks/`, and one folder under `Pages/Reports/` (page + widgets). Its widgets are appended to `DashboardPanelProvider::widgets()`. The sections below keep the short class names; the folder tells where each lives.

Rule for every report: names, labels and values are read from the master data and the existing resources, never copied into report files. Status lists, order and labels come live from the `statuses` table by the model's `TYPE_*` constant; the only fixed names are the status names code must recognise, taken from the existing status enums (`BankProfileResource\Enums\Status`, `CustomResource\Enums\ClearanceStatus`, `ShipmentResource\Enums\TrackingStatus`). There is no `config/reports.php`.

## `FxRateService` (euro base)

- `EUR_NAME = 'Euro'`: `eurCurrencyId()` returns the id of the active `currencies` row whose `english_name` is `Euro` (case-insensitive); production has one such row and no `EUR` key.
- `rate(int $from, int $to): ?array` — `['rate', 'bank_profile_id', 'date']` or null. Same currency is `1.0`. The rate comes from the latest bank profile (not trashed, status Purchased or Received per the Bank Profile enum, `requested_amount > 0`, `purchased_equivalent > 0`, both currency ids set), in either direction: `purchased_equivalent / requested_amount` when `requested_currency_id = $from`, the inverse otherwise; latest by `purchase_date` (nulls last) then id; a cache miss runs two small queries (the status ids, then the profile), and a missing pair is cached as a sentinel. Never `bank_profiles.exchange_rate`, `conversion_rate` or `final_rate`. There is no triangulation: a pair with no profile has no rate.
- `toEur($amount, ?int $currencyId): ?float` — null for a non-numeric amount, a null currency, a missing euro row or no rate; unchanged when already euro. A null result must never be dropped silently by callers: each report's stat card shows an «Excluded (no rate)» line naming the currency and amount left out of the euro total.
- Caching: a per-request memo plus `Cache::remember("reports:fx:{version}:{from}:{to}", 300)`; `FxRateService::flush()` clears the memo and bumps the cache version so every pair is invalidated. `ReportCheckObserver` calls it on every save/delete/restore of a bank profile, so a new or edited rate shows at once and the banner and check rows never disagree.
- Report widgets (attention table, charts) must be appended to `DashboardPanelProvider::widgets([...])`, otherwise their first Livewire round-trip throws "Unable to find component". The attention widget is embedded by the shared view with `...$attention::getDefaultProperties()`, which is what makes it lazy (a plain `@livewire(class)` is not).

## `ShipmentCurrencyResolver`

`resolve(Shipment)` / `resolveMany(Collection)` return `['currency_id', 'source' (invoice|order|proforma|null), 'mismatch']`. Precedence: the invoice header `currency` text (matched trimmed and case-insensitively to `currencies.name` or `english_name`, trashed currencies ignored), else the registered order's `currency_id`, else the first proforma's `main_currency_id`. `mismatch` is true only when the invoice currency resolved, the order currency exists and they differ. `resolveMany` is N+1-free: one query for the invoice headers of all shipments (`EntityAttribute` key `commercial_invoice`), one for the currency name map, relations loaded once; `resolve()` delegates to it. `invoiceHeader()` decodes the stored header twice when needed (production has one double-encoded `commercial_invoice` blob), so such a row neither throws nor loses its currency.

## `ReportStages`

- `ordered(string $englishType): Collection<Status>` — `StatusWorkflow::orderedStatuses()` when the Status master has a `stage_order` for the type (empty in production today), WITH every other live row of the type (not in the "shown apart" list) appended by id so a partial `stage_order` never drops a status (`withRemaining()`); otherwise the fallback order built from the enums (Bank Profile: Ready for Allocation → Awaiting Bank Review → Awaiting Supply → Allocated → Purchased → Received; Clearance: Documents Submitted → Declared → Appraisal → Pending Payment → Exit Gate → 10% Remaining → Completed; Tracking: the `TrackingStatus` case order), mapped to live rows, then every other live row of the type appended by id. Statuses shown apart (Bank Profile: Under Editing, Rejected, Documentary Bill; Clearance: Pending Editing) are excluded from the sequence.
- `index(Status): ?int`, `isAtOrAfter(Status, string $englishName): bool` over that sequence; `statusByName(type, name)` is a live memoised lookup; `inTransit()` / `arrived()` resolve `TrackingStatus::InTransit` / `ArrivedAtDestination` by name and return null when the Status master lacks them (the report then shows a "status not found" notice, never wrong numbers).
- Per-request memos; `ReportStages::flush()` clears them and also `CustomChecks::flush()` (the per-request memo of `validIdList()` and `clearedIds()` keyed by `cleared_from_stage`).

## `ReportFilters` (value object) and `HasReportFilters` (field factories)

- `ReportFilters` is final and immutable. `ReportFilters::fromArray(?array)` sanitises everything a Livewire filters form can carry — forged or garbage values never throw: non-numeric ids become null, bad dates null, unknown keys are ignored, a reversed date range is swapped, dates must be strict ISO `Y-m-d` (first 10 chars, year 1900–2200, real calendar day; «tomorrow» or garbage is null) and are normalised to start and end of day. URL/array keys are the snake form of the properties: ids (`seller_id`, `buyer_id`, `category_id`, `product_id`, `currency_id`, `registered_order_id`, `cost_center_id`, `bank_id`, `company_id`, `causer_id`, `purchased_currency_id`, `requester_id`), id lists (`status_id`, `clearance_status_id`, `shipment_status_id`), tokens and choices (`supply_source`, `module`, `activity_window`, `clearance_type`, `arrival_basis`, `departure_basis`, `date_basis`, `stage`, `quick`, `view_mode`, `weight_basis`, `value_basis`, `amount_in`, `rate_basis`, `commitment_state`), single ids (`bank_guarantee_status_id`, `commitment_status_id`, `cleared_from_stage`, `doc_status_id`), flags via `FILTER_VALIDATE_BOOL` (`show_closed`, `show_arrived`, `include_undated` default true, `include_void`, `include_flagged_invoices`, `include_outliers`, `fallback_order_amount`) and `idle_days`/`stuck_days`/`th_{key}` (whole numbers, 1–365 unless a key has its own bound). `toArray()` round-trips with `fromArray()`, `cacheKey()` is an md5 of the non-empty values sorted by key plus today's date, WITHOUT `quick` and `view_mode` (for `SmartCacheManager`), and `categoryIds()` returns the selected category plus every descendant from `category_closure` in one query (null when no category is chosen).
- Thresholds are self-service: `ReportFilters::THRESHOLD_DEFAULTS` (`idle_error` 14, `validity` 30, `supply` 30, `stuck` 30, `due_soon` 14, `arrive_1` 7, `arrive_2` 14, `late_error` 14, `late_grace` 0, `outlier_factor` 3, `supply_full` 99, `top_n` 5, `exceed_pct` 1, `commit_due` 30) are read through `threshold($key)` (`stuck` mirrors `stuckDays`, `idle` mirrors `idleDays`); form fields are `th_{key}` with `thresholdBounds()` (`late_grace` 0–365, `exceed_pct` 0–100, `supply_full` 1–100, `top_n` 1–20, `outlier_factor` 1–100, others 1–365). Defaults live ONLY in `ReportFilters` — a form `->default()` is applied before the URL state and was observed to be read instead of the URL value. The guide text uses `:th_{key}` tokens that `ReportPage::guide()` replaces with the live values.
- `Support\ReportDates::apply($query, $filters, $columns, $default)`: one date range for every report; `date_basis` picks the column from the report's own whitelist (unknown basis falls back to the default), and `include_undated` (default on) keeps rows whose basis date is NULL. `Support\SqlToday::literal()` is the only «today» in report SQL (a quoted `today()` date); `CURDATE()`/`NOW()` are banned and the MySQL connection timezone must never be changed (it would shift TIMESTAMP reads). `include_void` hides shipments whose status is Cancelled/Rejected unless on (`InTransitChecks::voidSqlFor`; the two names are the documented hard-coded exception). `show_closed` / `show_arrived` are the «show finished/closed» toggles of the reports that hide finished rows by default (R2 closed orders, R3 finished profiles, R5 cleared files, R7 cleared items, R4 arrived shipments).
- `App\Filament\Pages\Reports\Concerns\HasReportFilters` is a trait of static field factories named after the filter keys (the original set `getDateFromField`, `getSellerField`, `getBuyerField`, `getCategoryField`, `getProductField`, `getCurrencyField`, `getRegisteredOrderField`, `getCostCenterField`, `getBankField`, `getSupplySourceField`, `getCompanyField`, `getBankProfileStatusField`, plus per-report ones such as `getThresholdField($key)`, `getDateBasisField($options)`, `getIncludeUndatedField`, `getIncludeVoidField`, `getShowClosedField`, `getShowArrivedField`, `getDepartureBasisField`, `getWeightBasisField`, `getValueBasisField`, `getAmountInField`, `getRateBasisField`, `getCommitmentStateField`, `getRequesterField`, `getPurchaseRequestStatusField`, `getStageField`, `getCarrierField`, `getPurchasedCurrencyField`) plus the generic `getStatusField(string $name, string $labelKey, string $englishType, bool $multiple = false)`. Options are lazy closures over live master data: every ACTIVE row (currencies, companies, banks, products, departments; categories by `active`) whether or not any record uses it, in the Farsi name in `fa` and the English name otherwise. The status fields list every non-trashed status of the type: the `ReportStages::ordered()` sequence first, then the remaining live rows (the "shown apart" ones such as Under Editing) appended by id. Labels reuse existing keys (`resources/bankProfile/strings.filters.*`, `resources/product/strings.filters.category`, the bank-profile supply-source options) and add only `resources/report/strings.filters.*` for the rest, in en/fa/fr. Layout rule (owner, 2026-10-20): every page passes its field list through `HasReportFilters::arrangeFilters()` (main section and the collapsed «Advanced» section alike), which orders plain inputs first, then the wide selects (every multi-select plus the names in `WIDE_SELECTS`, each spanning two columns), then ALL toggles in one final row (a `Grid`, at most four columns), then nested sections; classification is by field name/type, never by reading a placeholder (a closure placeholder cannot be evaluated before the form is mounted and crashes the page). A new wide select must be added to `WIDE_SELECTS`. Each factory attaches a hover hint from `filters.hints.{key}` through `hinted()` (native `hintIcon` tooltip on every field, plus an `x-tooltip.raw` on the control itself for `Select`/`TextInput` only — `Toggle` has no input-attribute API and calling `extraInputAttributes` on it 500s the page, so the helper checks the field type); a new filter field must add its hint in all three locales.

## Data checks (`Check`, `CheckRegistry`, `Checks\*`)

- `Check` is a `final readonly` DTO: `key`, `model`, `severity` (`error`|`warning`|`info`), `reports`, `query` (offenders, soft-delete scope kept), `offending`, `expected`, `fix` (`resource`, `tab` lang key, `field`), optional `systemFix`; `messageKey()` / `expectedKey()` resolve `resources/report/strings.attention.checks.*`. A check never blocks a save.
- `CheckRegistry`: `all()` (nine check files: BankProfile, RegisteredOrder, Shipment, Custom, Correspondence, InTransit, Executive, Requester, FxCommitment), `forReport($report)` (also drops every check whose model the logged-in user cannot view — `{snake_model}.view`, e.g. `shipment.view` — so a report never lists problems of a module the viewer has no access to; no logged-in user means no filtering, and the cache keys already carry the user; a test user therefore needs the module's `.view` permission to see its issues). Two open gates by owner decision: `OPEN_TO_ALL` (`Correspondence`) skips the `.view` gate, and the `requester` report skips it entirely (R7's issues log is open to every R7 viewer). A check may belong to several reports (`reports` array); a key shared by two reports is intentional only where listed here (R4 checks reused by R1), `forRecord(Model)` (the checks the record currently offends), `evaluate(Check, ReportFilters)` — rows `['id','label','url','problem','offending','expected','severity','changed_by','changed_at','check']` from ONE offender query plus ONE batched who/when query (latest `audit` activity row, or `status_histories.user` for status fields); `counts($report, $filters)` — severity counts by COUNT query. Results are cached with `SmartCacheManager::remember('ReportCheck', …)` (key: kind, check, filters `cacheKey()`, user, locale, AND `isJalaliCalendar()` — cached `offending`/`expected` strings embed `adaptiveDate` text) for 5 minutes. `CheckRegistry::invalidate()` clears the `ReportCheck` cache and forgets the scoped singletons `FxCommitmentLedger`, `ExecutiveReportService`, `FxCommitmentsReportService`; it is called by `ReportCheckObserver` on save/delete/restore of any model in `AppServiceProvider::REPORT_CHECKED_MODELS` (BankProfile, RegisteredOrder, RegisteredOrderItem, Shipment, ShipmentItem, Custom, Correspondence, PurchaseRequest, PurchaseRequestItem, Payment, PurchaseOrder; `FxRateService::flush()` only for a BankProfile) and by `EntityAttributeObserver` when the saved attribute key is `commercial_invoice` (the invoice header holds the currency the ledgers read). The three singletons are registered with `$this->app->scoped(...)` in `AppServiceProvider::register()` so a queue worker gets fresh ones per job. Status-master edits are not observed (the TTL covers them).
- `Checks\BankProfileChecks::all()` (R3, all `reports = ['fx_supply']`): `purchased_without_equivalent`, `purchased_without_currency`, `purchased_without_purchase_date`, `allocated_without_allocation_date`, `missing_exchange_rate`, `requested_amount_zero`, `stuck_in_stage` (threshold `stuck`, default 30 = `STUCK_DAYS`; Received and Rejected excluded), `payment_due_soon` (threshold `due_soon`, default 14 = `DUE_SOON_DAYS`), `payment_overdue`, `status_invalid_type` (reads the status type through a select alias because `BankProfile::status()` is already restricted to its type), `status_missing` (error; owner decision: a profile with no `status_id` is flagged AND still listed by the open-payment checks, via `unsettled()` = `whereNull OR whereNotIn`, because `NOT IN` drops NULL), `no_status_history` (info). `HISTORY_AT`, `scoped()` and `statusIds()` are public so a report service reuses the same filter semantics. "Supplied" = Purchased or Received from the enum. Days in stage fall back to `updated_at` when a profile has no `status_histories` row (production's table is empty).

## R3 — `FxSupplyReportService` and `FxSupplyReport`

- `FxSupplyReportService` implements `ReportService`: `query()` = the bank-profile query scoped by `BankProfileChecks::scoped()` plus a `days_in_status` select (latest `status_histories` row, else `updated_at`, flagged by `without_history`), relations eager-loaded; `summary()` = exactly four cards: queued (Ready for Allocation / Awaiting Bank Review / Awaiting Supply), allocated, «purchased» (current calendar month via `CalendarRange::forMonth` so Jalali months work; with a date range the card becomes «purchased in the selected period» and uses the PURCHASE date only — `scopedFor()` forces `date_basis=purchase_date` and `include_undated=false` for that card, quick key and CSV, so the page's creation-date basis cannot double-restrict it) and «Timing and payments» (average days creation→allocation and allocation→purchase, payment due soon within `due_soon` days [`payment_due_soon`], overdue [`payment_overdue`], and a «finished hidden» line while finished profiles are hidden); by default finished profiles are hidden from the table and cards (`BankProfileChecks::showsFinished/notFinished`, toggled by `show_closed`, an explicit finished status filter wins); amounts are grouped per currency and never summed across currencies, the euro total comes from `FxRateService::toEur` and a currency with no rate appears on an "Excluded (no rate)" line; `rows()`/`exportLabels()` share one column whitelist (labels reuse the bank-profile lang keys); `chartFunnel()` counts per `ReportStages` stage (rendered as a doughnut), `chartByBank()` sums the queued amount per bank with one dataset per currency (grouped bar).
- `Pages\Reports\FxSupplyReport` (key `fx_supply`, permission `report.view_fx_supply`, sort 3) reuses the resource's `BankProfileResource::show*` columns; `FxSupplyFunnelChart`, `FxSupplyByBankChart` and `FxSupplyAttentionWidget` are registered as described above.
- Page order in the shared view (`resources/views/filament/pages/reports/report.blade.php`, the same for all seven reports): the guide accordion (first, tabs inside) → filters (one full-width accordion titled `filters.heading`, collapsed by default, built in each page's `filtersForm()`; rarely used accuracy toggles and thresholds sit in a nested collapsed «Advanced» section) → four stat cards (4 per row on desktop, 2 per row on mobile) → analytics (the charts, rendered by `ReportPage::analytics()` from the page's `analyticsWidgets()`, not as header widgets) → table → ONE accordion, collapsed by default, headed "N open data issues": the severity chips on top, then (after a divider) the attention table. It appears only when the report has issues; the attention table is embedded by the shared view through `ReportPage::attention()`, not as a footer widget. The banner's Error / Warning / Note chips dispatch the Livewire event `report-severity`; `ReportAttentionWidget::filterBySeverity()` listens, sets its `severity` table filter (which only evaluates checks of that severity) and "Show all" clears it.
- Quick keys (clickable summary lines): `queued` / `allocated` / `purchased_month` = the «Profiles» line (that card's status set; purchased_month also its `CalendarRange` month on `purchase_date`), and `{card}_currency_{id}` = that set AND the currency the card groups by (requested currency for queued/allocated, PURCHASED currency for purchased_month; `_currency_0` = the dash line, `IS NULL`). `cardSet()` is the single source for both the card aggregate and `applyQuick()` (called last in `query()`), so they cannot drift; unknown/malformed keys leave the table unchanged. The euro total, «Excluded (no rate)» and average-days lines have no key; charts, checks and cards never read `quick`.
- Lang: `resources/report/strings.fx_supply.*` plus the `status_missing` check texts, en/fa/fr.

## R2 — `OperationsReportService` and `OperationsReport`

- `OperationsReportService` (implements `ReportService`): `query()` = one row per OPEN registered order (`RegisteredOrderChecks::openOrders()`: filters from `RegisteredOrderChecks::scoped()` plus decision D4 — closed only when every live shipment has at least one customs row and EVERY customs row has the enum's `Completed` status — one unfinished or status-less customs file keeps the order open; no shipments = open) with select aliases `stage` (a `CASE` over `EXISTS` sub-queries: customs → shipment → payment → bank profile → registration; payment = a payment on the order itself OR on a purchase order linked to exactly that one order, the `AnalyticsService::orderPaymentsSql` rule written as correlated `EXISTS`, since MySQL forbids outer references inside derived tables), `idle_days`, `last_activity_at`, `last_ref`, `idle_from_updated_at`, `purchase_orders_count`. An `afterQuery` hook runs `FileRowLoader::load()` for the page's rows: ONE batched query per concern (bank-profile statuses → highest by `ReportStages` order, latest shipment, latest customs, latest correspondence with recipients, statuses, last activity / status-change rows, users). `STAGES` (pipeline order, label keys = the existing model labels), `summary()` (four cards: open files by stage, idle files, order validity, priority correspondence), `chartStages()`, `rows()` / `exportLabels()`.
- `Support\FileActivity`: the last-activity sub-query — `UNION ALL` of `activity_log` (`log_name = audit` only; calendar rows never count) and `status_histories` for the order and its bank profiles / shipments / customs, `GROUP BY` order; `last_ref` (`a|s : id : actor`) comes from `SUBSTRING_INDEX(GROUP_CONCAT(... ORDER BY at DESC))`, so truncation of a long group keeps the newest entry. Days idle = `FileActivity::idleSql()` = `DATEDIFF(<SqlToday literal>, COALESCE(last_at, updated_at, created_at))`, flagged `idle_from_updated_at` when no activity row exists.
- `Support\ActivityFeed`: `query()` is a SQL `UNION ALL` of audit rows and status-history rows inside the `activity_window` (24h / 7d / 30d, default 7d), narrowed by `causer_id` and `module` (snake class name from `AuditChanges::MODELS`) and ALWAYS limited to `AuditChanges::viewableModels()`; `rows()` hydrates one page in batches (`AuditChanges::fields()`, statuses, users, subjects → file number). The order number of a subject is its own `ro_number` or its `registered_order_id`; subjects without one show «-». Pagination is done in SQL (no cap).
- `Checks\RegisteredOrderChecks` (reports `['operations']`): `idle_over_threshold` (warning; threshold `idle` = the `idle_days` filter, default `ReportFilters::IDLE_DAYS` 7), `idle_over_14` (error; threshold `idle_error`, default 14), `validity_expiring` (warning; threshold `validity`, default 30), `validity_expired` (error), `no_items` (error), `no_bank_profile_after_n_days` (warning; threshold `supply`, default 30), plus `missing_validity_date`, `missing_party`, `missing_currency`, `in_customs_without_payment_or_bank_profile`. All run on OPEN orders only. Validity rule (owner): an order is expired when its Validity Date is BEFORE today (today is not expired) AND it has no purchase order (`RegisteredOrderChecks::UNFULFILLED_SQL`); the same rule feeds the card, the quick keys, the checks and the table badge. `ShipmentChecks::missing_tracking_status` (warning), `CorrespondenceChecks::open_high_priority` (warning). A stray status of another type or a name outside the clearance enum is an admin data-entry issue and is NOT a report check (`custom.clearance_status_invalid` was removed).
- R2's `summary()`, `chartStages()` and `chartIdleByStage()` are cached through `SmartCacheManager::remember('ReportCheck', …)` for 5 minutes (key: kind, filters `cacheKey()` which carries today, locale) because `FileActivity::latest()` is an uncorrelated aggregate over the whole audit log; the observer invalidation above keeps it fresh on saves. Day counts use `FileActivity::idleSql()` (built on `SqlToday::literal()`). There is no Correspondence status enum: the owner defines a correspondence as closed when its status is «Approved» or «Archived» (`CorrespondenceChecks::CLOSED_STATUSES`); the check lists every `high`/`urgent` correspondence not closed that is attached to an open order, its shipments or its customs.
- `ReportFilters` additions: `causerId`, `activityWindow`, `module`, `idleDays` (whole floats from Filament number inputs are accepted by `id()`); `HasReportFilters` additions: `getRegisteredOrderStatusField`, `getActivityWindowField`, `getCauserField`, `getModuleField`, `getIdleDaysField` (no form `->default()` on them — the defaults live in `ReportFilters`; a field default is applied before the URL state and was observed to be read instead of the URL value).

The resolver test pins the constant query count of `resolveMany`; the attention-widget cases in `ReportPageBaseTest` tell rows apart by a check's `expected` text, never its `message` (the message also renders in the check-filter dropdown, so `assertDontSee` on it can never pass) and never by `bp_number` (`CodeGeneratingObserver` overwrites it and `BP-261019` is a substring of `BP-261019-1`); the filter-field cases in `ReportPageBaseTest` assert under `fa` and `en` that an active unused row is listed, an inactive row is not, and labels resolve in all three locales.
