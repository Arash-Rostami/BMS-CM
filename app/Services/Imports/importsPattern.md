# Shared Import Pipeline (`app/Services/Imports/`)

## Why this exists

Purchase Request's bulk-import feature was originally built as a long sequence of incremental, per-module patches directly on `App\Filament\Traits\ImportDefaults` (per-column static helpers) and each concrete `{Module}Importer` class (`afterFill()`-inline fallback/reject logic). When the same shape was then duplicated wholesale into Proforma Invoice, a cross-module coupling bug surfaced immediately (`ProformaInvoiceImporter` importing PR's own namespaced `GroupRowFailedException`) — concrete proof the per-module-memory approach doesn't scale. This directory is the replacement: **one shared service, declarative per-column composition, a real `Illuminate\Pipeline\Pipeline`-driven runtime** — a module adopts it by declaring its columns once, not by remembering every rule.

**Leftover pre-rewrite test files, cleaned up 2026-09-26.** Two test files kept asserting against the OLD architecture this section describes as replaced, and had been silently failing every full-suite run since — repeatedly mis-flagged as "pre-existing, unrelated" by three separate review passes rather than actually resolved. `tests/Feature/Filament/PurchaseRequestImportTest.php` instantiated `PurchaseRequestItemImporter` standalone with a flat `pr_number` column expecting it to self-resolve its parent from row data — the current architecture requires an explicit `forParent()` call (only ever done by `PersistChildRows`/`forGroup()`), so every test in that file threw `LogicException`; deleted outright, its coverage (end-to-end create+items, reupload-in-place, Persian-digit numeric parsing) is 100% superseded by `PurchaseRequestResourceTest.php`'s current `invokeMergedImporter()`-based tests. `tests/Feature/Traits/ImportDefaultsTest.php` had 2 tests calling a `booleanColumn()` helper that no longer exists (`ImportDefaults` now holds only genuine Importer-lifecycle glue, per this section) — removed those 2 tests only, kept the other 13 (still testing current, real behavior). **If a full-suite run ever again shows a failure a review calls "pre-existing," verify that claim by reading the actual failing test before accepting it — a stale leftover from an architecture rewrite reads identically to a real regression until someone checks.**

## The column taxonomy — four shapes, not three

A column is declared once in a module's `importColumns(): ImportColumnDefinition[]`, composed from independent, chainable behaviors:

| Shape | How it's built | Meaning |
|---|---|---|
| **Match** | `::match($name, $labelKey, $relation, $model, $resolveColumns)` / `::matchStatus(...)` / `::matchEnum(...)` / `::matchCountry(...)` | A provided CSV value is resolved against a DB relation, a `Status` row, a 3-locale translation-key enum map, or (for `matchCountry`) the `App\Services\Country` static list by en/fa name or ISO code. Rejects the row if a NON-BLANK value doesn't resolve. |

**`matchStatus()` columns are workflow-aware on NEW records, added 2026-09-26.** `Stages/ApplyColumnFallbacks.php` (a `BEFORE_SAVE_STAGE`, already gated on `! $context->record->exists`) checks every column with a non-null `statusType` against `StatusWorkflow::initialFor($type)` — if that type has at least one ordered (`stage_order`-set) status, the new record's status is force-set to that initial status, **overriding whatever the CSV cell resolved to**, before the row saves. A bad/unresolvable CSV value still throws `RowImportFailedException` at cast time as before (`ImportColumnFactory::applyStatusMatch()` itself is unchanged) — only a value that successfully resolved gets silently overridden afterward. Existing records (re-uploads) are completely unaffected — they keep whatever `applyStatusMatch()` resolves normally, exactly as before this addition. For a type with no ordered statuses (every module except Purchase Request as of this writing), `initialFor()` returns null and this is a no-op — the shared pipeline behaves identically to before. Rationale: without this, a bulk CSV import could set any status (e.g. "Authorized") with zero permission check, completely bypassing the approval-gating a resource's own Filament form enforces — see `filamentPattern.md` §1.12b.
| **Fallback** | `->withFallback($closure, includeInTemplate: bool, rejectIfStillBlank: bool)`, chainable onto ANY of the above | Supplies a value when the column is blank, but only on a NEW record (an update never gets a fallback-overwritten value). |
| **Optional** | `::optional($name, $labelKey, ...)` | No match, no fallback — a plain passthrough column. Blank stays blank (`ignoreBlankState()`), filled gets cast and saved. |
| **Manual-set** | `::manualSet($name, $labelKey)` — sugar for `optional()->withFallback(fn () => null, rejectIfStillBlank: true)` | No default is possible; a blank value on a new record is a hard reject. |

**Match and Fallback are NOT mutually exclusive** — this was a real design bug caught mid-build (the first draft made them exclusive categories, which would have silently dropped the DB-lookup/relationship binding for `department_id`/`requester_id`/`cost_center_id`/`main_currency_id`, columns that must resolve a *provided* value AND default when blank). `ImportColumnDefinition::hasMatchConfig()` and `::hasFallback()` are independent booleans; `ImportColumnFactory::build()` dispatches purely on which properties are set (`relation`/`statusType`/`enumTranslationKey` vs `isDate`/`isNumber` vs plain), and the pipeline stages check `hasFallback()`/`rejectIfStillBlank()` independently of match config.

"Reject" is never a fifth category — it's the row-level OUTCOME when a Match fails to resolve a non-blank value, or when a Fallback-with-`rejectIfStillBlank` is still blank after the fallback ran.

**Settled policy, decided 2026-10-05: every `match()`/`matchStatus()`/`matchEnum()`/`matchCountry()` column bound to a `NOT NULL` DB column must chain `->withFallback(fn () => null, rejectIfStillBlank: true)` (or a real fallback value that itself never resolves to blank) — never leave a NOT-NULL match column with no fallback at all.** Match handles a NON-BLANK unresolved value (rejects or nulls per `allowNullOnMismatch()`); it says nothing about a genuinely BLANK cell, because `ImportColumnFactory::build()` calls `->ignoreBlankState()` unconditionally on every column — a blank cell never even reaches the match/cast logic, it's skipped by Filament's own `fillRecord()` before `afterFill()` runs. Without a fallback, a blank value on a NEW record sails straight through to `saveRecord()` and dies as a raw, untranslated SQL NOT-NULL `QueryException` — the one failure mode this whole pipeline exists to avoid. Check this per-column against the table's REAL migration, never guessed: a nullable column is fine left bare (blank legitimately saves as `null`); a NOT-NULL column with a DB-level `->default(...)` is also fine left bare (MySQL fills the default when the PHP attribute is never set); only a genuinely NOT-NULL, no-default column needs the explicit fallback. This is the same `->withFallback(fn () => null, rejectIfStillBlank: true)` shape `manualSet()` already uses — a match column just chains it manually since `manualSet()` itself has no match config. Applies equally to a `matchStatus()` column whose fallback resolves via `Status::findBy(...)?->id`: that call can itself return `null` if the looked-up status name doesn't exist, so `rejectIfStillBlank: true` is still required even though a fallback closure is already present — a present-but-null-resolving fallback is not the same guarantee as a reject-if-still-blank one.

**One real, structural exception — don't "fix" it on a false-positive reading of the rule above.** `product_id` on all 4 item importers (`PurchaseRequestItemImporter`, `ProformaInvoiceItemImporter`, `PurchaseOrderItemImporter`, `RegisteredOrderItemImporter`) is a bare `match()` on a genuinely NOT-NULL, no-default column with NO fallback chained — found by a `claude-reviewer` pass, 2026-10-05, auditing this exact rule for completeness. It's safe anyway because `product_id` IS each module's `itemDiscriminatorColumn` for `GroupedImportAction::groupRows()` — a row with that cell blank is never routed to the item importer at all; it's either reclassified as a new parent-row boundary or rejected outright as `item_without_product` before any importer column logic runs. The protection is real, just structural (classification-level) rather than column-level — don't add a `withFallback()` chain here on the assumption it's missing.

**`withFallback($closure, ?bool $includeInTemplate, bool $rejectIfStillBlank)`'s second parameter defaults to `null` ("keep the value already set"), NOT `true`.** Fixed 2026-09-22 (found by an independent Fable 5 review): it used to default to `true` unconditionally, so `::optional('x', $label, includeInTemplate: false)->withFallback($fn)` — omitting the parameter on the fallback call — would silently re-show a column in the sample file that the base constructor had deliberately hidden. No current column definition happened to hit this (every `includeInTemplate: false` column also passes it explicitly to `withFallback()`), but don't rely on that — always pass `includeInTemplate` explicitly to `withFallback()` when the base definition set it to `false`.

## The two-phase pipeline

```php
ImportPipeline::runBeforeSave($context)   // ApplyColumnFallbacks -> RejectMissingManualColumns
ImportPipeline::runAfterSave($context)    // PersistChildRows -> SyncEavAttributes -> RunModuleRecalculation
```

`runBeforeSave()` is called from each parent importer's `afterFill()` — a real Filament `Importer` lifecycle hook that fires AFTER `fillRecord()` but BEFORE `saveRecord()`. This ordering is load-bearing: `department_id`/`requester_id` etc. are `NOT NULL` DB columns (verified via `SHOW COLUMNS`, not guessed), so if the fallback/reject stages ran in `afterSave()` instead, the FIRST `saveRecord()` call would hit blank NOT NULL columns and throw a raw, untranslated `QueryException` before the pipeline ever got a chance to fill or cleanly reject them — defeating the entire point of the reject-cleanly design. `runAfterSave()` is called from `afterSave()` (after the record has a real ID) since child-row persistence and EAV sync both need the parent's FK.

Item (child) importers run only `runBeforeSave()` from their own `afterFill()` — they have no children of their own, no EAV, no recalculation.

`ImportRowContext` (`app/Services/Imports/ImportRowContext.php`) carries the row's Eloquent `$record`, its `columns` (the module's `ImportColumnDefinition[]`), and (for the after-save phase) `pendingChildRows`/`pendingExtraAttributes` populated by the parent importer before the pipeline runs. `$context->options['__importer']` carries the concrete importer instance itself, which `PersistChildRows`/`RunModuleRecalculation` duck-type against (`method_exists($importer, 'childImporterInstance')`, `method_exists($importer, 'recalculateAfterPersist')`).

**`PersistChildRows` fails loudly (`LogicException`), not silently, if a row has pending child rows but the importer doesn't implement `childImporterInstance()`** — added 2026-09-22 after an independent review (Fable 5) flagged that the original duck-typed no-op would let a future module silently drop every child row it queued. Covered by `test_persist_child_rows_fails_loudly_when_pending_rows_have_no_child_importer_hook` in `tests/Feature/Services/Imports/ImportPipelineTest.php`.

**Grouped-group atomicity re-verified 2026-10-05, with real evidence, not just re-stated from the architecture.** `ImportDefaults::runInTransaction()` wraps EVERY importer's own `__invoke()` (parent AND child alike) in its own `DB::transaction()` call. Since `App\Jobs\ImportGroupedCsv::handleGroups()` already wraps its whole per-chunk `foreach ($groups as $group)` loop in one outer `DB::transaction()`, every parent/child `DB::transaction()` call made while iterating a group runs NESTED — Laravel turns a nested `DB::transaction()` into a real MySQL `SAVEPOINT`, not an independent commit. When a later item row in the same group throws (`RowImportFailedException`/`ValidationException` inside `PersistChildRows`, rethrown as `GroupRowFailedException`), that exception propagates up through the PARENT's own `DB::transaction()` closure, which rolls back to the parent's savepoint — undoing the parent row AND every item row already inserted earlier in that same failed group — before `ImportGroupedCsv`'s outer catch logs the failure and the loop moves on to the NEXT group unaffected. Proven directly, not just reasoned about: `PurchaseRequestResourceTest::test_import_duplicate_product_within_same_group_is_rejected` and `RegisteredOrderResourceTest::test_import_second_item_failing_rolls_back_the_first_already_persisted_item_and_the_parent` each insert a first item successfully, then force a second item in the same group to fail, then re-query both the parent table and the item table after the `GroupRowFailedException` to confirm the counts are back to their pre-import baseline — zero rows survive for a group that didn't fully succeed.

## `App\Contracts\Imports\Importable`

```php
interface Importable
{
    public static function importColumns(): array;   // ImportColumnDefinition[]
    public static function eavEnabled(): bool;        // gates whether getColumns() appends the 5 EAV pairs — now actually read; used to be declared+implemented but never consumed anywhere, fixed 2026-09-22
    public function recalculateAfterPersist(): void;  // no-op if the module has nothing to recalculate
}
```

Implemented by both current PARENT importers (`PurchaseRequestImporter`, `ProformaInvoiceImporter`). Item importers do NOT implement this interface — they declare `importColumns()`/`getColumns()` the same way (for consistency and so the generic `autoFilledColumnNames()` trait method works on them too), but the interface itself is only meaningful for a module's top-level, `GroupedImportAction`-wired importer. Child-row wiring (`childImporterInstance()`/`forGroup()`) is deliberately NOT on this interface — not every future module will have child rows, and forcing the method onto modules that don't need it would be speculative; `PersistChildRows`' loud-failure guard (above) is what actually protects a module that *does* have pending child rows but forgot to wire the hook.

## Country matching (`matchCountry`, Proforma Invoice only, added 2026-09-22)

`ImportColumnFactory::applyCountryMatch()` builds a `[lowercased name/code => ISO code]` map from `(new App\Services\Country)->all()` — a new public accessor added to `Country` for this (the class previously only exposed locale-scoped, single-locale views via `getCountriesList()`/`getCountryNameByCode()`; import matching needs BOTH `name` (fa) and `name_english` (en) simultaneously, regardless of the importing session's locale, same reason `LocalizedMatcher::enumMap()` merges all 3 locales for enum columns). Accepts the Farsi name, the English name, or the raw 2-letter ISO code; stores the ISO code, matching what the FORM's own `Select::options((new Country)->getCountriesList())` fields store. Used by `ProformaInvoiceImporter`'s `beneficiary_country`/`origin_country`/`destination_country` (parent-level). The item importer's `origin` field (per-item country of manufacture — also a `Country`-backed `Select` on the form, see `Form.php::getItemOriginField()`) is NOT yet wired to `matchCountry` — still plain `optional()` — deliberately not changed without being asked, since it's a distinct field from the 3 the user named.

## EAV (Purchase Request only, so far)

`ImportDefaultsShared::extraAttributeColumns(int $pairs = 5): array` builds 5 fixed `extra_key_N`/`extra_value_N` `ImportColumn` pairs — Filament's column-mapping wizard needs a fixed, pre-known column list, so this is deliberately NOT arbitrary-column EAV detection. `extraAttributeMapFromData(array $data, int $pairs = 5): array` reads the raw import row data (before `fillRecord()` strips the `extra_*` keys) into a `key => value` map, silently skipping any pair whose key is blank (never saves an empty-string attribute).

`SyncEavAttributes` calls `$record->syncCustomAttributes($map)` ONLY when the map is non-empty — **this guard is load-bearing, not defensive padding**: `syncCustomAttributes()` deletes every existing `EntityAttribute` not present in the passed map, so calling it with `[]` on a re-uploaded row (one whose CSV simply didn't mention EAV columns at all) would silently wipe that record's existing custom attributes. Covered by `test_import_does_not_wipe_existing_custom_attributes_when_extra_pairs_are_blank` in `PurchaseRequestResourceTest.php`.

`Importable::eavEnabled()` gates whether `getColumns()` appends the 5 pairs at all — `PurchaseRequestImporter::eavEnabled()` returns `true`, `ProformaInvoiceImporter::eavEnabled()` returns `false` (no EAV import for PI yet). A module returning `true` here without ALSO wiring `beforeFill()`'s `extraAttributeMapFromData()` call and `afterSave()`'s `pendingExtraAttributes` assignment would build the columns but never actually sync them — `eavEnabled()` only controls column visibility, it doesn't wire the rest of the plumbing automatically.

## Hiding auto-set columns from the mapping wizard

Filament's column-mapping step builds one `Select` row per `getColumns()` entry with no server-side "hide this row" API (verified against vendor `ImportAction.php`: `array_map(fn (ImportColumn $column) => $column->getSelect()->options(...), $importer::getColumns())` — every declared column gets a row, unconditionally). Removing a column from `getColumns()` entirely was considered and rejected as the general mechanism — it would silently stop Filament from reading ANY CSV data for that field, even when a header happens to match, since `fillRecord()` only reads mapped columns. This is exactly why `pr_number`/`invoice_no` (the SCANNABLE_IDENTIFIER each module's `resolveRecord()` matches an existing record by, for re-upload/update-in-place) stay VISIBLE and mappable — hiding them would silently break update-matching. Currently only PR's `requester_id`/`department_id` use `includeInTemplate: false`; PI has no hidden columns at all.

Instead, `App\Filament\Actions\ImportAction::buildAutoFilledColumnHidingStyle()` generates a `<style>` block from the SAME `autoFilledColumnNames()` list the accordion guide already reads — no column name is hardcoded anywhere. It's appended to `modalDescription()`'s output alongside the guide:

```php
protected function buildAutoFilledColumnHidingStyle(): string
{
    $autoFilledColumns = $this->getImporter()::autoFilledColumnNames();
    $selectors = collect($autoFilledColumns)
        ->map(fn (string $column) => '[data-field-wrapper]:has(select[wire\:model$="columnMap.'.$column.'"])')
        ->implode(',');

    return $autoFilledColumns ? '<style>'.$selectors.'{display:none}</style>' : '';
}
```

A future module's auto-filled columns are hidden automatically the moment they're declared `includeInTemplate: false` — no CSS file edit, ever. The fields stay fully present and functional in the form (still mappable, still submit correctly, still drive `resolveRecord()`/fallback logic) — only their visual row is suppressed, so the mapping step doesn't clutter the user with columns they never need to look at. Covered by `test_import_modal_description_renders_the_accordion_guide_without_crashing` (PR, asserts the hide selectors for `requester_id`/`department_id`) and `test_import_modal_description_hides_no_columns_when_nothing_is_auto_filled` (PI, asserts the empty-list branch emits no style tag at all).

## Two downloadable samples: blank template vs. filled example

`App\Filament\Actions\ImportAction` registers two modal link actions, each its own row (wrapped in separate `<div>`s so they don't render inline):

- **`downloadExample`** — the BLANK template: header row only, columns filtered by `autoFilledColumnNames()`. Vendor's own label for this action is misleadingly `"Download example CSV file"` despite having zero data rows (no `ImportColumn` in this codebase ever calls `->example()`/`->examples()`) — overridden to `resources/general/strings.import.download_blank_template` to stop calling an empty file an "example."
- **`downloadFilledExample`** — a real, realistic filled file: multiple parent groups, several with 2-3 item rows (multiple products per parent — the answer to "how do I import several products," which is row-per-product, not EAV-shaped). Only rendered when the importer declares `filledExamplePath(): ?string` (duck-typed via `method_exists`, same idiom as `autoFilledColumnNames()`), served from `storage_path('app/'.$path)` (Laravel's `local` disk root is `storage/app/private/` in this version, NOT `storage/app/` — the file lives at the plain `storage_path('app/...')` path directly, bypassing the `Storage` facade's `local` disk entirely to avoid that mismatch). All three grouped-import modules now have one:
  - `PurchaseRequestImporter::filledExamplePath()` → `storage/app/import-examples/purchase-request-filled-example.csv` — includes EAV pairs on a couple of rows (PR is the only EAV-enabled module).
  - `ProformaInvoiceImporter::filledExamplePath()` → `storage/app/import-examples/proforma-invoice-filled-example.csv` — 2 groups, real seller/buyer/currency/country/product values verified to resolve against the actual dev DB (a `filledExamplePath()` pointing at a file that doesn't exist yet throws a raw `FileNotFoundException` straight out of the download action — reproduced live 2026-09-22 before the file was created; always create and dry-run-verify the file in the SAME change that wires `filledExamplePath()`, never wire the method first and add the file "later").
  - `RegisteredOrderImporter::filledExamplePath()` → `storage/app/import-examples/registered-order-filled-example.csv` — **this exact warning was reproduced live again 2026-09-25**: RO's initial build shipped without `filledExamplePath()` wired at all (module has no filled example, only the auto-generated blank template) — caught and fixed the same session, not by the original build, but by a follow-up dry-run pass. 3 groups: one demonstrating `pr_numbers` pivot-attach against a real existing PR, one plain two-currency-type example, one deliberately using an unresolvable `incoterms` value to demonstrate the null-on-mismatch-plus-note behavior rather than a row rejection. **The dry-run-verify step is not optional decoration** — running this file through the real importer end-to-end (not just asserting the file exists) caught a genuine, separate bug: `RegisteredOrderItemImporter`'s `quantity`/`unit_price` columns were declared `::optional(..., isNumber: true)` with no fallback, copied from Proforma Invoice's item importer where those same two columns ARE nullable in the DB — but `registered_order_items.quantity`/`.unit_price` are NOT NULL with no default, so a blank value used to crash with a raw, untranslated `QueryException` (`Field 'unit_price' doesn't have a default value`) instead of cleanly rejecting the row — exactly the failure mode `runBeforeSave()`'s ordering was designed to prevent (see "The two-phase pipeline" above), just missed on these two columns specifically. Fixed by adding `->withFallback(fn () => null, rejectIfStillBlank: true)` to both, matching `unit`'s existing treatment on the same importer. **Lesson: a column being `optional()` in a sibling module's importer is not evidence it's safe to copy `optional()` verbatim onto a same-named column in a new module — always check that specific module's own migration nullability, every time.**

## Modal heading — never let Filament auto-pluralize a translated label

`Filament\Actions\Concerns\InteractsWithRecord::getPluralModelLabel()` falls through to `Str::plural($singularLabel)` when no table/custom plural label is set — Laravel's `Str::plural()` only knows English inflection rules, so calling it on a Farsi string can literally append a Latin "s" to Farsi text. Both `PurchaseRequestResource`/`ProformaInvoiceResource`'s `getImportAction()` now set `->modalHeading(...)` explicitly to the SAME already-correct translated string already used for `->label(...)` — never rely on Filament's automatic pluralization for a label sourced from a non-English translation.

## Jalali/Gregorian options — verified both directions, plus a live helper text

`getOptionsFormComponents()`'s `jalali` `Toggle` now has `->live()` + `->helperText()` showing which calendar is currently selected ("اکنون تقویم شمسی است" / "اکنون تقویم میلادی است" in fa) — updates immediately on toggle, no page reload. Not covered by an automated test (a `Toggle`'s live helper-text closure needs a real bound Schema/Livewire container to evaluate — `Field::getHelperText()` throws `must not be accessed before initialization` on a bare component with no container, and the options form itself only renders once a file is selected in the real modal, making a full Livewire-integration test non-trivial for a cosmetic detail) — this matches `tests/testPattern.md` §2's documented exception for Filament-internal reactive plumbing.

The actual date-parsing logic (`ImportColumnFactory::applyDate()`) IS fully covered, both directions: `test_import_parses_a_valid_jalali_date_with_persian_digits_to_the_correct_gregorian_value` (Persian-digit Jalali input, `jalali: true`, verified against a real `Morilog\Jalali\CalendarUtils` conversion — 1404-01-01 → 2025-03-21) and `test_import_parses_a_valid_gregorian_date_with_mixed_digit_scripts_to_the_correct_value` (Arabic-Persian digit Gregorian input, `jalali: false`) in `PurchaseRequestResourceTest.php` — plus three clean-rejection tests (invalid Jalali date, invalid Gregorian date via `checkdate()`, and a fully malformed string) confirming every bad-date path throws `RowImportFailedException`, never a raw crash.

**Every column with a date fallback gets a guide line naming the actual default, per-module.** `ImportAction::buildImportGuideHtml()` adds a "If a date is left blank" section only when the importer declares `dateDefaultsSummary(): ?string` (duck-typed, same idiom as `filledExamplePath()`/`autoFilledColumnNames()`) — `PurchaseRequestImporter` returns `resources/purchaseRequest/strings.import.date_defaults` ("required by date + 1 month"), `ProformaInvoiceImporter` returns `resources/proformaInvoice/strings.import.date_defaults` ("invoice date → today; validity date → import date + 2 weeks"). Each module's own lang file's `import` group carries this key — not `resources/general/strings.php`, since the actual default varies per module and per column.

## Import is never wired into a RelationManager — fixed 2026-09-22

`ImportDefaults::resolveRecord()` matches on `SCANNABLE_IDENTIFIER` with a completely global, unscoped query (`$model::withTrashed()->where($identifier, $value)->first()`) — no `ImportAction`/`GroupedImportAction` code path has any awareness of a Filament `RelationManager`'s owner record. `PurchaseRequestResource::getImportAction()` used to be wired into 3 PR-showing relation managers (`RegisteredOrderResource`/`PurchaseOrderResource`/`ProformaInvoiceResource`'s own `PurchaseRequestsRelationManager`) alongside `AttachAction`. This was a real, confirmed danger: importing a CSV from inside, say, Registered Order #42's "Purchase Requests" tab, where one row's `pr_number` happened to match an *existing* PR belonging to a completely different, unrelated Registered Order, would silently UPDATE that unrelated PR's fields — with no warning it wasn't related to the current context, and no auto-attachment to the current owner either (so the tab you were working in showed nothing changed, while a different order's data was quietly mutated elsewhere).

**Fixed by removal, not by scoping.** All 3 relation managers now offer only `AttachAction::make()` (attach an existing PR — safe, explicit, one record at a time) — bulk import stays exclusively on `PurchaseRequestResource`'s own top-level list page, where "match any existing PR globally" is the correct, expected behavior. Scoping the import to the owner (constrain `resolveRecord()`'s match query + auto-attach via the pivot afterward) was considered and explicitly rejected as the fix — it's real new plumbing (passing owner-record context through the pipeline, per-module pivot-attach logic), not a quick change, and the user's bar for this was "no risk," not "engineer around the risk."

**Proforma Invoice was never at risk and stays as-is.** PI's relation managers (under PurchaseRequest/PurchaseOrder/RegisteredOrder) only ever had the safe pattern — a `Prepares{Target}From{Parent}` trait-driven auto-populate `create` Action that pre-fills the new record's form (including the relationship field) via a URL query param, with the user reviewing and submitting the form themselves; nothing silent, nothing auto-saved, nothing globally-scoped. `ProformaInvoiceResource::getImportAction()` has zero relation-manager call sites and was deliberately not added to any, for the same "no risk" reason — building a genuinely scoped/auto-attaching bulk import for PI's relation-manager contexts was considered and declined until there's a real design for owner-scoped matching, not before.

**The general rule going forward**: `getImportAction()`/`GroupedImportAction` must never be wired into a `RelationManager`'s `headerActions()` for ANY module, current or future, unless the import pipeline is first given real owner-record awareness (scoped `resolveRecord()` matching + auto-attach). Until that plumbing exists, a relation manager gets `AttachAction` (existing records) and/or a `Prepares*From*`-driven single auto-populate create (new records) — never bulk import.

## Settled policy — decided 2026-09-25, do not re-ask in future module work

These are final design decisions for any future module adopting this pipeline (Registered Order's own importer — **built 2026-09-25**, see the pivot-attach and denylist-fix notes below — was the first to apply them). Don't re-litigate them per-module — apply directly.

**Pivot-attach columns for a module whose parent has `belongsToMany` relations (new territory, Registered Order's `pr_numbers`/`invoice_nos`/`po_numbers`).** These aren't real DB columns, so they're never declared via `ImportColumnDefinition` — that would `data_set()` a non-existent model attribute. Instead: (1) build them as plain `Filament\Actions\Imports\ImportColumn`s directly (same idiom as `ImportDefaultsShared::extraAttributeColumns()`'s EAV pairs — `ignoreBlankState()` + a trimming `castStateUsing()`, no relation/match config at all), included in `getColumns()` so the mapping wizard can see them; (2) in `beforeFill()`, read the raw comma-separated value out of `$this->data` BEFORE `unset()`-ing it (same order as the item-column-stripping idiom), split/trim it, and stash `{relation, model, identifierColumn, label, values}` entries on the importer instance; (3) in `afterSave()`, copy that array onto the new `ImportRowContext::$pendingPivotAttaches` property (empty by default, so every OTHER module's `runAfterSave()` call is unaffected) before calling `ImportPipeline::runAfterSave()`. The actual attach work is `App\Services\Imports\Stages\AttachPivotRelations` — registered in `ImportPipeline::AFTER_SAVE_STAGES`, genuinely module-agnostic (no Registered-Order-specific code in the stage itself): for each identifier, `{model}::query()->where(identifierColumn, value)->first()` resolves it, a hit gets batched into a `syncWithoutDetaching()` call (additive only — never detaches a pivot row the CSV doesn't mention, and naturally idempotent against a duplicate on re-upload), a miss gets appended to the record's own `notes` via the SAME `resources/general/strings.import.unresolved_match_left_blank` message `AppendUnresolvedMatchNotes` uses (not a bespoke string) followed by an explicit `$record->save()` — this stage runs post-save, so (unlike the pre-save note-appending stage) mutating `notes` here needs its own persist call. A future module reuses this stage for free by populating `pendingPivotAttaches` the same way; no stage code changes needed.

**The `id`/`user_id`/`updated_by_id`/`*_type` column denylist (`ImportDefaults::assertColumnNamesAllowed()`) had a real false positive, fixed alongside Registered Order.** It used to reject ANY column name ending `_type` (a heuristic proxy for "this app's polymorphic morph-discriminator columns"), which wrongly blocked `currency_type` — a genuine, `$fillable`, plain string column on `registered_orders`, not a morph discriminator. Fixed by naming the schema's actual five morph-type columns explicitly (`attachable_type`, `entity_type`, `targetable_type`, `correspondable_type`, `specifiable_type`) instead of guessing from the suffix — strictly more precise, no loss of protection (a real morph `*_type` column is never mass-assignable on the writing side of the relation, so an explicit list catches every column the suffix heuristic was ever meant to catch, plus nothing it wasn't). A future module with its own legitimately-fillable `*_type` column benefits automatically — don't reintroduce the blanket suffix check.

**List re-audited 2026-10-05 against every `morphTo()`/`morphs()`/`nullableMorphs()` in the current schema — two more real morph-type columns were missing and have been added: `notifiable_type` (`notifications` table) and `statusable_type` (`status_histories` table, `StatusHistory`'s own audit-trail morph).** Neither was an active exploit (no importer declares either column today), but the list is meant to be a complete, proactive guard, not one that only grows reactively after a near-miss — the explicit list is now 7 entries: `attachable_type`, `entity_type`, `targetable_type`, `correspondable_type`, `specifiable_type`, `notifiable_type`, `statusable_type`. Re-run this same audit (grep every model for `morphTo(` + every migration for `morphs(`/`nullableMorphs(`) whenever a new polymorphic relation is added anywhere in the app, not only when building a new importer.

**Match-column mismatch: reject vs. null.** For any match-shaped column (`match`/`matchEnum`/`matchStatus`/`matchCountry`), the row rejects on a non-blank unresolved value ONLY when the underlying DB column is NOT NULL (business-required). If the DB column is nullable, the column resolves to `null` instead of rejecting — but the original raw value is never silently discarded: `AppendUnresolvedMatchNotes` (a `runBeforeSave()` stage, after `ApplyColumnFallbacks`) appends it to the record's own `notes` field (`[Import] {column label}: could not match "{raw value}" — left blank`, one line per mismatched column, existing notes preserved, never overwritten). API: `ImportColumnDefinition`'s `rejectOnMismatch` (default `true` — every column's existing behavior is unchanged unless explicitly opted out), set via `->allowNullOnMismatch()`. **Default every new column to strict reject; opt into null-on-mismatch only when the DB column is genuinely nullable and "garbage optional data" should degrade gracefully instead of killing the row.** Retrofitted onto PI's `secondary_currency_id`/`beneficiary_country`/`origin_country`/`destination_country`/`transport_mode`/`delivery_terms` and PR's `cost_center_id` (all confirmed nullable). Left strict: PI's `seller_id`/`buyer_id`/`main_currency_id`, PR's `requester_id`/`department_id`/`urgency_level` (the last NOT NULL despite having a DB default — deliberately excluded), and PR's `status_id` — deliberately excluded despite being nullable, decided 2026-09-25 after an independent review flagged it: `status_id` changes drive `PurchaseRequestObserver`'s cascade to child items on Authorized/Declined, so a typo on re-upload silently stalling that workflow transition (with only a buried `notes` line as evidence) is worse than the row rejecting loudly. **Nullable is necessary, not sufficient for the null-on-mismatch opt-in** — a column whose value drives a real side effect (an observer, a cascade, a status-gated permission) stays strict even when the DB allows null.

`ImportColumnFactory::applyRelationMatch()` uses TWO different mechanisms depending on the flag, not one branch of the same code — this is load-bearing, not a stylistic choice. The strict path still calls `->relationship($name, resolveUsing: ...)` (`fillRecord()`'s built-in `$relationship->associate(...)`). The null-on-mismatch path deliberately does NOT call `->relationship()` at all — it resolves manually via `castStateUsing()` and writes the FK id directly, exactly like `matchStatus`/`matchEnum`/`matchCountry`. Reason: vendor `ImportColumn::getDataValidationRules()` unconditionally appends its OWN "exists" validation rule whenever `hasRelationship()` is true (`vendor/filament/actions/src/Imports/ImportColumn.php`), completely independent of whatever closure `->rules()` was given — so simply skipping our own `$fail()` call when `rejectOnMismatch` is `false` is not sufficient, the vendor rule still fails validation underneath us. Confirmed live 2026-09-25. Don't "simplify" the lenient branch back to a shared `->relationship()` call without re-solving this.

**A null-on-mismatch column on an UPDATE (re-upload) row does not literally overwrite an existing value to `null`.** `ImportColumnFactory::build()` calls `->ignoreBlankState()` on every column (unconditionally, for the pre-existing "a blank cell in a re-uploaded CSV preserves the existing value" contract). Since `castStateUsing` collapses BOTH "genuinely blank" and "non-blank but unresolved" down to the same `null` cast value, `Importer::fillRecord()`'s `blank($state) && $column->isBlankStateIgnored()` skip cannot tell them apart — a mismatch on an update row is therefore treated exactly like leaving that cell blank: the row is not rejected, the PRE-EXISTING value survives untouched, and `AppendUnresolvedMatchNotes` still logs the raw text (it re-derives the mismatch independently via `ImportColumnFactory::build($column)->castState($raw)`, never by reading `$context->record`'s post-fill state, specifically so the note fires correctly regardless of this skip). On a NEW record with no prior value, this is indistinguishable from a real null write. Confirmed via `PurchaseRequestResourceTest::test_import_reupload_with_unresolvable_cost_center_and_status_preserves_the_existing_values_and_logs_a_note` and PI's mirrored `test_import_reupload_with_an_unresolvable_secondary_currency_preserves_the_existing_value_and_logs_a_note`.

**Identifier fallback — always via `CodeGenerator`, never a hard reject.** A module's own re-upload match identifier(s) (PR's `pr_number`, PI's `invoice_no`, any future module's) fall back to an auto-generated value on a blank NEW record via `fillReservedNumberIfBlank($field)` (called from `beforeCreate()`) → `CodeGenerator::generate($field)`. Never `rejectIfStillBlank` on an identifier column. A module with more than one `CodeGenerator`-mapped identifier (e.g. Registered Order's `ro_number` + `contract_no` — two independent prefixes already registered in `CodeGenerator::$map` for the same model) calls `fillReservedNumberIfBlank()` once per column; each gets its own independent reserved-number sequence, no special-casing needed.

**Date-fallback shape — pick by real semantics, not by copying the nearest example.** PR's `required_by_date` (`now()->addMonth()`) is the template for a "required/expected by" date with no more specific rule given. PI's `validity_date` (`now()->addWeeks(2)`) is the template when the meaning is "how long does this quote/offer stand," not "how soon do we need this." Check which shape actually fits the target column before defaulting to either.

**`unit` column convention.** Always `matchEnum('unit', $label, 'resources/general/strings.metrics')` — a fixed, 3-locale list, never free-text passthrough. Whether it also gets `->withFallback(fn () => null, rejectIfStillBlank: true)` follows the general mismatch policy above, keyed off the target module's own DB nullability — check the migration, don't copy PI's or PR's shape blind.

**Pin the import AND export column count in every module's master test file.** One assertion (`assertCount($n, {Module}Importer::getColumns())` / the exporter's equivalent) per module, with a one-line comment explaining why the number is pinned. Reason: BankProfile's exporter silently shrank from 38 columns to 12 during this session's rewrite (narrowed to match the importer's set instead of staying an independently comprehensive reporting artifact) and nobody caught it until manual inspection — no test asserted a column COUNT, only that specific named columns existed. Export is not required to mirror import's column set; it usually shouldn't, since export is a reporting/audit surface and import is a data-entry surface with different scope. A future refactor that drops or adds columns must fail this test loudly, not slip through.

## Two exporter-conversion checks, missed on Payment's first pass and caught by review (2026-10-04)

**Escape EVERY free-text column, not just the obviously long ones.** Payment's conversion routed `beneficiary_name`/`beneficiary_address`/`bank_address`/`notes` through `plainText()`'s formula-escaping, but left `account_no`/`swift`/`iban` as raw casts — all three are unrestricted `TextInput` fields with no character allow-list, so each is just as capable of carrying a formula-injection payload as the fields that got escaped. When converting a native `Exporter` to the flat `write()` shape, audit the SOURCE FORM's field types (`Traits/Form.php`), not just the old `ExportColumn` list — any plain `TextInput`/`Textarea` column needs `plainText()`, regardless of how short or "structured-looking" (an account number, a SWIFT code) its value appears.

**Eager-load every relation a computed DISPLAY method reads, not just the columns directly selected.** Payment's `targetable` export column calls `$record->getTargetableDisplay()`, which internally reads `formatted_name`/`formatted_name_without_date` on the morphed target — for a `PurchaseOrder` that's `creator`+`status`, for a `RegisteredOrder` it's `sellerCompany`+`buyerCompany`. A bare `'targetable'` in the eager-load list (no `morphWith([...])`) still lets the column render correctly, just via a lazy-loaded query per row — an easy-to-miss N+1 since nothing errors or looks wrong, it's only slow. Before pinning an exporter's eager-load list, trace every computed/accessor-backed column's own relation reads, not just what the column's name implies.

## Payment — the third FLAT consumer, and the first to resolve a polymorphic (`morphTo`) target, added 2026-10-04

`PaymentImporter` mirrors Bank Profile/Department's flat wiring (plain `App\Filament\Actions\ImportAction` + `App\Jobs\ExportPayments`, `eavEnabled(): false`, no item importer). Column plan covers every `payments` column except `id`/`user_id`/`updated_by_id` and the `targetable` pair: `payment_no` (identifier, `fillReservedNumberIfBlank`), `payment_date` (`withFallback(fn () => now())`), `payment_deadline` (plain `optional()`, no fallback — no clear default rule), `status_id`/`payor_id`/`payee_id`/`currency_id`/`bank_id` (all nullable FKs, `allowNullOnMismatch()` — Payment has no observer/cascade tied to any of these, unlike PR's `status_id`), `payable_amount`/`total_amount`/`exchange_rate`/`bank_charges` (all `withFallback(fn () => 0, rejectIfStillBlank: false)` — DB defaults to 0), the beneficiary/bank text fields and `notes` (`optional()`).

**`targetable_type`/`targetable_id` cannot be declared via `ImportColumnDefinition` at all** — `ImportDefaults::assertColumnNamesAllowed()`'s denylist explicitly blocks the literal name `targetable_type` (and every other real morph-discriminator column in the schema), by design, to stop a generic import column from mass-assigning a polymorphic type. Payment is the first module whose import needs to SET a morph target rather than avoid touching one, so this needed new (not previously covered by settled policy) plumbing:

- Two plain `Filament\Actions\Imports\ImportColumn`s — `purchase_order_number`/`registered_order_number` — same idiom as a pivot-attach column (`ignoreBlankState()` + trimming `castStateUsing()`, no relation/match config), included in `getColumns()` so the mapping wizard sees them, but NOT built via `ImportColumnFactory`/`ImportColumnDefinition` and therefore never passed to `assertColumnNamesAllowed()`.
- Resolved in `beforeFill()`: read both raw values out of `$this->data`, `unset()` both immediately (same "read before strip" order as the pivot-attach idiom — Filament's `fillRecord()` would otherwise try to `data_set()` a non-existent model attribute and the later `save()` would throw an unknown-column `QueryException`), then:
  - both given → reject (`targetable_ambiguous`).
  - one given but doesn't resolve to a real `PurchaseOrder`/`RegisteredOrder` row → reject (`targetable_not_found`).
  - one given and resolves → `$this->record->targetable_type`/`targetable_id` are set DIRECTLY as a plain property assignment — the exact same "intentionally bypass the denylist via explicit code, not generic column assignment" idiom `fillReservedNumberIfBlank()` already uses for `payment_no`.
  - neither given, NEW record → reject (`targetable_required`). Neither given, EXISTING record (re-upload matched via `payment_no`) → leave the existing `targetable_type`/`targetable_id` untouched, consistent with the pipeline's general "blank preserves existing value" contract.

**A future module with its own polymorphic (`morphTo`) import target reuses this exact shape** — two identifier-style helper columns resolved manually in `beforeFill()`, never a bare `ImportColumnDefinition` named after the real `*_type`/`*_id` columns. This is now the precedent; don't re-invent a different mechanism for the next one.

`PaymentExporter::write()` mirrors `BankProfileExporter::write()`'s shape exactly (no `itemRow()` — Payment has no child rows). Same 31-column scope the old native `Exporter` already had — converting its shape didn't change what it reports (unlike Bank Profile's conversion, there was no narrowing/widening decision to make here). Converting it broke two sibling call sites exactly the same way every prior exporter conversion did — `RegisteredOrderResource`'s and `PurchaseOrderResource`'s own `PaymentsRelationManager`s each referenced `ExportBulkAction::make()->exporter(PaymentExporter::class)` directly; both repointed to `PaymentResource::getExportBulkAction()`.

Filled example: `storage/app/import-examples/payment-filled-example.csv`, 4 rows (2 targeting real `PurchaseOrder`s, 2 targeting real `RegisteredOrder`s), dry-run verified end-to-end against the real dev DB.

## Product — the fifth FLAT consumer, and the first with a DELIBERATE reject-on-duplicate identity rule, added 2026-10-06

`ProductImporter` mirrors Bank Profile/Department's flat wiring (plain `App\Filament\Actions\ImportAction` + `App\Jobs\ImportCsv`, `eavEnabled(): false`, no item importer) with one settled, user-confirmed deviation from every other module's identity contract: **`code` is never a re-upload match/update identifier.** `resolveRecord()` is overridden directly (not the trait default) — a blank code rejects (`resources/product/strings.import.code_required`), and a code that already belongs to ANY existing Product (soft-deleted or not — collation on `products.code` is `utf8mb4_unicode_ci`, confirmed case-insensitive, so a case-variant duplicate is already caught for free) rejects as well (`resources/product/strings.import.duplicate_code`), always returning a fresh `new Product` otherwise. This matches the live create form's own inquiry-gated flow (editing an existing product only ever happens through the Edit action).

**Specification fields are NOT `ImportColumnDefinition`s** — `hs_code`/`import_duty`/`packing_type`/`vat_exempt`/`tax_id`/`manufacturer`/`import_licenses`/`extra` live on the polymorphic `Specification` model (`specifiable_type`/`specifiable_id`), not on `products`. Declaring them as ordinary columns would let Filament's default `fillRecord()` call `data_set($product, 'hs_code', ...)` and crash the INSERT with an unknown-column `QueryException` the first time a row populated one. Instead they're 8 plain `Filament\Actions\Imports\ImportColumn`s (same `ignoreBlankState()` + trimming `castStateUsing()` idiom as Payment's `targetable` helper columns), read out of `$this->data` and `unset()` in `beforeFill()` (before `fillRecord()` ever runs), stashed on the importer instance, and only persisted in `afterSave()` via `$this->record->specifications()->updateOrCreate([], $pendingSpecification)` — and only when `ProductResource::specificationHasData()` (the same guard the live Repeater uses, see `filamentPattern.md` §1.6's `defaultItems(0)` note) says at least one of the 8 fields is non-blank. A row whose specification fields are all blank creates zero `specifications` rows — proven by the filled example's own `PRD-IMP-003` row. `attributes` (a genuine `products` JSON column) stays a normal flow-through column, just hand-built instead of `ImportColumnDefinition`-based, since it needs a comma-explode cast no existing taxonomy shape provides.

**New taxonomy shape: `ImportColumnDefinition::boolean($name, $labelKey)`.** `in_stock`/`is_active` are real, NOT NULL `products` columns with a DB default of `true` — the existing shapes had no boolean cast at all (`optional()`'s plain-text cast would hand a raw string like `"yes"` straight to `data_set()`, and MySQL strict mode throws `Incorrect integer value` on save rather than silently coercing it). `ImportColumnFactory::applyBoolean()` recognizes `1/true/yes/on` and `0/false/no/off` (case-insensitive, trimmed) and returns `null` for anything else or blank — degrading gracefully into the column's own `->withFallback(fn () => true, rejectIfStillBlank: false)` exactly like every other null-on-mismatch column. Reusable by any future module with a genuine boolean import column; don't re-invent a bespoke cast for one.

**`AppendUnresolvedMatchNotes` gained a `Schema::hasColumn($table, 'notes')` guard, added alongside Product.** The stage unconditionally wrote `$context->record->notes = ...` on any null-on-mismatch column — fine for every prior consumer (all have a `notes` column), but `category_id`'s `allowNullOnMismatch()` column on Product would have crashed the very first garbage-category-name row with the same unknown-column `QueryException` class as the specification-fields landmine above. Rather than leave `category_id` strict (losing the "garbage input degrades gracefully, nullable column" contract) or skip the note silently in just one module, a nullable `notes` TEXT column was added to `products` (`database/migrations/2026_10_06_100000_add_notes_to_products_table.php`, `$fillable`, and a read-only infolist `TextEntry` — mirrors every sibling operational model's `notes` field) and the stage itself was hardened to no-op when the resolved record's table has no such column at all, memoized per-table in a static array so the guard costs one `Schema::hasColumn()` call per distinct model per request, not per row. This is a shared-infra fix: every future flat/grouped consumer with a nullable null-on-mismatch column but no `notes` field benefits automatically, not just Product.

`ProductExporter::write()` mirrors `DepartmentExporter`'s shape (no `itemRow()` — `specifications` is a zero-or-one morph relation, read via `$record->specifications->first()`). 24 columns, wider than import's 16 (export stays an independent reporting surface per the BankProfile precedent above — `id`, category/name/code/attribute columns, every specification field, `creator`/`updater`/both audit dates. `import_licenses` and `extra` are both round-trippable: the exporter joins `import_licenses` (a JSON array of license KEYS) through the SAME `resources/product/strings.form.licenses` label map the form's `Select` uses, comma-joined, and `ProductImporter`'s own parser accepts either the translated label OR the raw key back (reverse-lookup against the same map) — so an export → edit-in-Excel → reimport round trip is lossless in either direction, not just key-preserving. `extra`'s `key: value| key2: value2` packed format is intentionally identical on both sides (export produces it, import parses it) — a malformed pair (no `:`, or a blank key) is dropped and appends one `[Import] extra: could not parse "..." — skipped` line to the new `notes` column, never rejects the row; well-formed pairs in the same cell still save.

Filled example: `storage/app/import-examples/product-filled-example.csv` (no blank-template file — matching every other module in this project, the blank template is generated dynamically by Filament's own `downloadExample` action from `getColumns()`, never a static file). 4 rows: a fully-populated specification row, a row demonstrating the malformed-`extra`-pair note plus a well-formed pair saved alongside it, a row with every specification field blank (proves no `specifications` row is created), and a row with an unresolvable `category_id` (proves the null-on-mismatch degrade — `category_id` ends up `null`, the row still imports, dry-run verified against the real dev DB's actual category names for the resolvable rows).

## Bank — the sixth FLAT consumer, and the second CREATE-ONLY reject-on-duplicate importer (after Product)

`BankImporter` mirrors Bank Profile/Department's flat wiring (plain `App\Filament\Actions\ImportAction` + `App\Jobs\ImportCsv`, `eavEnabled(): false`, no item importer, no `dateDefaultsSummary()` — no date columns) and applies the same deliberate deviation from the standard match-then-update `resolveRecord()` that `ProductImporter` established above. Both `banks.name` and `banks.english_name` are enforced unique only at the Filament FORM layer (`->unique(..., modifyRuleUsing: fn ($rule) => $rule->withoutTrashed())` in `Traits/Form.php`) — there is **no real DB unique index** on either column (confirmed against the migration), so editing an existing Bank only ever happens through the Edit action, never by re-submitting a matching name/english_name via import. `BankImporter::resolveRecord()` is fully overridden to:

1. Reject a blank `english_name` outright (`resources/bank/strings.import.english_name_required`) — this is the field the dedupe check keys on.
2. Reject if `Bank::where('english_name', $value)->exists()` (default scope — soft-deleted rows excluded, matching the form's own `withoutTrashed()` modifier exactly) — `resources/bank/strings.import.duplicate_bank`.
3. Reject if `Bank::where('name', $value)->exists()` too (same message key) — a row could pass the `english_name` check yet still collide on `name`, since the two columns are independently unique on the form. **Product's own `resolveRecord()` doesn't need this second check since `code` is Product's only unique business key — a future module with two independently-unique columns should check both, same as Bank does.**
4. Only then `assertRequiredColumnsForNewRecordsPresent()` and `return new Bank`.

**Collation note**: the `banks` table uses the app's default `utf8mb4_unicode_ci` collation (case-insensitive), so the plain `=` comparison in both `exists()` checks matches a case-variant duplicate exactly the same way Laravel's own `unique` validation rule does on the live form.

**`is_active` boolean handling — built independently of `ImportColumnDefinition::boolean()` above, now redundant, flagged for consolidation.** `BankImporter` was built in a parallel, isolated worktree with no visibility into Product's work landing the same session — it solves the identical "no native boolean cast in this pipeline" problem via its own local `castStateUsing()` post-processing on the built `ImportColumn` (`BankImporter::castIsActive()`, recognizing `1/true/yes/active`/`0/false/no/inactive`, blank/unrecognized → `null` → falls through to the fallback) rather than the shared `ImportColumnDefinition::boolean()` factory shape. Both are functionally correct and independently reviewed; **a follow-up pass should migrate `BankImporter` (and `CurrencyImporter`/`CompanyImporter`, which hit the same gap the same way) onto the shared `ImportColumnDefinition::boolean()` helper** so there's one boolean-cast implementation in the pipeline, not three. Until that consolidation happens, don't be confused that two different-looking boolean solutions coexist — neither is wrong, they're just not yet unified.

`BankExporter::write()` mirrors `DepartmentExporter::write()`'s shape (no `itemRow()` — Bank has no child rows), 9 columns (`id`, `name`, `english_name`, `description`, `is_active`, `creator`, `updater`, `created_at`, `updated_at`) — one fewer than Department since Bank has no `code` column. Filled example only: `storage/app/import-examples/bank-filled-example.csv`.

## Category — a flat consumer with no real business identifier, create-only, reject-on-duplicate

`CategoryImporter` mirrors Department/Bank Profile's flat wiring (plain `App\Filament\Actions\ImportAction` + `App\Jobs\ExportCategories`, `eavEnabled(): false`) but is the first module with NO `CodeGenerator`-mapped identifier column at all — `slug` is auto-derived by `HasSlug`'s `saving` boot hook from `english_name`, never user input, never importable. Identity is resolved by computing what `HasSlug` would produce (`Str::slug($englishName)`) and checking it against the real `categories.slug` column (confirmed `utf8mb4_unicode_ci` — case-insensitive — so a same-name-different-casing row correctly collides): a match REJECTS the row rather than updating it, via a fully custom `resolveRecord()` override that never calls the shared `ImportDefaults::resolveRecord()`/`SCANNABLE_IDENTIFIER` path — every row this importer ever creates is a brand-new `Category`, there is no update-in-place story at all (same deliberate deviation as the sibling Product importer).

Column plan: `english_name` (`manualSet` — the reject-if-blank required field; `resolveRecord()`'s own slug-collision check is the real duplicate gate, this column just guards blank), `name` (`optional()`), `parent_id` (a `match()` against `Category` by `['name', 'english_name']`, `allowNullOnMismatch()` — nullable FK, no fallback needed, same shape as Bank Profile's `company_id`), `description` (`optional()`), `active` (`optional()` + `withFallback(fn () => true, rejectIfStillBlank: false)`, manually coerced from string to a real boolean in `afterFill()` since this pipeline has no dedicated boolean column type). **`level` is deliberately EXCLUDED from the import column set entirely — never a CSV column, never user-supplied** — unlike the live form's own plain, unchecked `TextInput`, a bulk import multiplies a single bad `level` value across many rows with zero error, silently corrupting hierarchy-depth queries. Instead `CategoryImporter::afterFill()` derives it server-side, strictly from the already-resolved `parent_id`, after `ImportPipeline::runBeforeSave()` has run: `$record->level = $record->parent_id ? Category::find($record->parent_id)->level + 1 : 0`, making a mismatch structurally impossible. `afterFill()` also re-applies the same `Category::wouldCreateCycle()` guard the live form's parent `Select` uses (see `app/Filament/filamentPattern.md`'s Category form section) before deriving `level` — structurally a no-op under this importer's create-only `resolveRecord()` (a brand-new row has no id yet, so it can never be its own ancestor), kept only for interface parity should this importer ever grow an update path.

**Found and fixed while building this module: `Stages/AppendUnresolvedMatchNotes` assumed every consuming model has a `notes` column.** Every prior `allowNullOnMismatch()` consumer (Bank Profile, Payment, Proforma Invoice) happens to have one; `categories` does not, so the very first garbage `parent_id` value on a Category import would have thrown a raw, untranslated `Unknown column 'notes'` `QueryException` instead of cleanly leaving the FK null. Fixed by gating the note-append on a `Schema::hasColumn($table, 'notes')` check, memoized per-table in a static array for the life of the PHP process (table shape doesn't change without a deploy/restart, unlike the per-row `Status` lookup cache `applyStatusMatch()` already memoizes) — every existing consumer's behavior is unchanged, a future `notes`-less model is now safe by construction. Covered by `test_append_unresolved_match_notes_does_not_crash_for_a_model_with_no_notes_column` in `ImportPipelineTest.php`.

`CategoryExporter::write()` mirrors `DepartmentExporter::write()`'s shape exactly (no `itemRow()` — Category has no child-row relation). Keeps the same 10-column set the prior native `Exporter` subclass had (id, both names, level, parent, active, creator, updater, both audit dates) — `name`/`english_name`/`parent` (the parent's own `name` column, unlocalized — same literal behavior the old `ExportColumn::make('parent.name')` had) routed through `plainText()`, `active` resolved via the existing `Enums\Status` enum (reuses the table column's own localized Active/Inactive labels rather than new export-only keys).

Filled example: `storage/app/import-examples/category-filled-example.csv` — 4 rows, two independent root categories each followed by one child row whose `parent_id` cell names the immediately-preceding row's own `english_name` (Electronics → Mobile Phones, Furniture → Office Chairs), dry-run verified end-to-end against the real dev DB; the last row also demonstrates a blank `description` and `active=0`.

## Currency — the seventh FLAT consumer, and the second CREATE-ONLY dual-column reject (after Bank)

`CurrencyImporter` mirrors Bank Profile/Department's flat wiring (plain `App\Filament\Actions\ImportAction` + `App\Jobs\ImportCsv`, `eavEnabled(): false`, no `dateDefaultsSummary()`), but `currencies` has no natural identifier column at all — `resolveRecord()` is fully overridden (not `ImportDefaults`'s default `SCANNABLE_IDENTIFIER`-driven version) and never returns an existing record: a blank `english_name` throws `RowImportFailedException` (`resources/currency/strings.import.english_name_required`), and a duplicate on EITHER `english_name` OR `name` throws the same `duplicate_currency` exception — settled 2026-10-06 to match `BankImporter`'s dual-column check (both columns are independently unique on the live form, so checking only one leaves a real gap). Column plan (4 total, pinned by `test_import_and_export_column_counts_are_pinned`): `name`/`english_name` (`manualSet` — both reject-if-blank; the `resolveRecord()` override above is the real duplicate gate for both), `description` (`optional()`), `is_active` (`optional()->withFallback(fn () => true, rejectIfStillBlank: false)`, with a local `castStateUsing()`/`rules()` pair normalizing `yes/no/1/0/true/false/active/inactive` tokens to a real boolean and rejecting anything else via `resources/general/strings.import.invalid_option` — the shared `ImportColumnDefinition::boolean()`/`ImportColumnFactory::applyBoolean()` primitive Product's own import build introduced for the same need isn't wired in here yet, flagged for the same consolidation pass as `BankImporter`'s).

The duplicate check (`Currency::where('english_name', $value)->exists()`) relies on `english_name`/`name`'s real collation (`utf8mb4_unicode_ci`/`utf8mb4_persian_ci`, both case-insensitive — verified via `SHOW CREATE TABLE currencies`, not guessed) for case-insensitive matching, and — like the form's own `->unique(...)->withoutTrashed()` rule — implicitly excludes soft-deleted rows via Eloquent's default `SoftDeletingScope`, so a trashed currency's `english_name` is free to reuse on import, consistent with (not a gap against) the manual-create form's behavior.

**Authorization is narrowed to `canCreate()` alone, not the shared `resourceGate()` helper** (`canCreate() && canEdit(null)`) every other importer in this codebase uses — justified here specifically because `resolveRecord()` never returns an existing record (see above), so there is no update path for `canEdit` to gate. Don't copy this narrowed shape onto a future importer without first confirming its own `resolveRecord()` is equally incapable of returning an existing record.

`CurrencyExporter::write()` is the 9-column reporting mirror (both names, description, localized active/inactive, creator, updater, both audit dates), BOM + formula-escape + Jalali support, dispatched via `App\Jobs\ExportCurrencies` (see `app/Jobs/jobsPattern.md`). The filled example sample lives at `storage/app/import-examples/currency-filled-example.csv`.

## Known gaps (found by an independent Fable 5 review, 2026-09-22 — not yet fixed)

- **`department_id` is both hidden from the downloadable sample file (`includeInTemplate: false`) and hard-required (`rejectIfStillBlank: true`)** — a deliberate, user-confirmed tradeoff (the sample file excludes truly system-only columns even though the edge case of "importing user has no department on file" still rejects the row) — but the accordion guide text doesn't currently mention this edge case. Low-risk copy fix, not yet made.
- ~~A MySQL deadlock mid-chunk can roll back the whole `ImportGroupedCsv` chunk-level transaction while the per-group loop keeps incrementing `successful_rows` for groups that no longer exist~~ — **fixed 2026-10-05.** `ImportGroupedCsv::handleGroups()`'s per-group `catch` chain used a single generic `catch (Throwable)` that silently absorbed a deadlock-classified `QueryException` exactly like any other row-level failure — `report()` + `logGroupFailure()` + keep looping — even though MySQL had already rolled back the ENTIRE enclosing transaction, including every group that loop already counted as successful. Fixed with a dedicated `catch (QueryException $exception)` branch that checks `ImportDefaults::isDeadlock($exception)` (widened from `protected` to `public` for this — the Job class needs to call it on `$this->importer`, which isn't `self`/`static` from the Job's perspective) and re-throws instead of absorbing it, plus the outer `DB::transaction($closure)` call gained a 3rd `$attempts = 3` argument — mirroring the exact retry shape `HasReliableCodeGeneration` already uses for the same deadlock class (`modelsPattern.md` §3). The closure now also resets `$processedRows`/`$successfulRows`/`$this->failedRows` to empty at its own top, required so a genuine Laravel-triggered retry re-runs the whole chunk from a clean slate instead of double-counting whatever the doomed first attempt had already tallied before dying.
  **A real constraint surfaced while testing this, not a limitation of the fix**: Laravel's own `ManagesTransactions::handleTransactionException()` only retries a deadlock at the OUTERMOST transaction nesting level (`$this->transactions > 1` throws `Illuminate\Database\DeadlockException` immediately, no retry, by Laravel's own explicit design — see the comment in that vendor method). Every test in this suite already runs inside its own outer `DB::beginTransaction()` per `testPattern.md` §0's mandatory isolation skeleton, which makes the Job's own `DB::transaction($closure, 3)` call a NESTED transaction from the test's point of view — so the "retry succeeds and the chunk completes" path is structurally untestable under this project's own test convention, not just hard to simulate. What IS fully, deterministically testable (and is what `tests/Feature/Jobs/ImportGroupedCsvTest.php`'s two new tests cover): a deadlock-classified exception propagates out instead of being silently logged as a normal row failure (`test_handle_propagates_a_deadlock_instead_of_silently_logging_it_as_a_normal_row_failure`), and a genuinely different, non-deadlock `QueryException` still gets caught and logged exactly as before, no behavior change for the common case (`test_handle_still_logs_a_non_deadlock_query_exception_as_a_normal_row_failure`). Both constructed via a decorator wrapping the real `PurchaseRequestImporter` instance (swapped in via `ReflectionProperty` on the Job's `protected Importer $importer` property) that throws a fabricated-but-realistic `QueryException` (the inner `PDOException`'s message must contain the literal string `"Deadlock found when trying to get lock"` — Laravel's `ConcurrencyErrorDetector` matches on message text for anything that isn't a bare `PDOException`, not just the `errorInfo` SQLSTATE/driver-code pair `isDeadlock()` itself checks) on the first call, delegating to the real importer on any later call — no real concurrent connections needed for the parts that genuinely can be tested this way.
- ~~`ImportColumnFactory::applyStatusMatch()` runs one uncached `Status::where(...)` query per row per status column~~ — **fixed 2026-10-05.** Mirrors vendor `ImportColumn::$resolvedRelatedRecords`'s own lifecycle exactly, confirmed by reading it first: that property is a plain instance array on `ImportColumn`, and `Importer::getCachedColumns()` builds a fresh `ImportColumn` list (`$this->cachedColumns ??= ...`) per `Importer` instance — which itself is constructed fresh per queued `ImportCsv`/`ImportGroupedCsv` job (one job per CSV chunk; see `vendor/filament/actions/src/Imports/Jobs/ImportCsv.php`'s constructor). `applyStatusMatch()` is a static factory method with no instance of its own to hold state on, so the memoization lives as a local `$resolved = []` array declared inside `applyStatusMatch()` and captured BY REFERENCE (`use (&$resolved)`) into the `castStateUsing` closure attached to that one `ImportColumn`. Because the local array is created fresh every time `applyStatusMatch()` runs (once per status column, every time `getColumns()`/`cachedColumns` is rebuilt), the cache's lifetime is bound to one `ImportColumn` instance — it cannot outlive the chunk/job that built it, and a long-running queue worker processing a second, unrelated import job later gets a brand-new array, never stale data from a `Status` row edited/deleted in between. Keyed on `"{$type}|{$value}"` (the two inputs that actually vary a lookup — `$type` happens to be invariant within one column's closure, but the key is built explicitly this way so the cache stays correct if that ever changes) and caches BOTH a resolved `Status` and a confirmed miss (`array_key_exists`, not `isset`), so a repeated unresolvable value in the same chunk also stops re-querying. Deliberately NOT `SmartCacheManager`/`Cache::remember` — those are request/process-lifetime with their own invalidation story, the wrong shape for a cache that must die with the chunk. Covered by two new tests in `ImportPipelineTest.php`: `test_status_match_column_memoizes_lookups_for_the_lifetime_of_the_built_column` (5 `castState()` calls with the same value against one built column, `DB::getQueryLog()` shows exactly 1 `statuses` query, not 5) and `test_status_match_column_cache_does_not_leak_across_separately_built_columns` (a second, separately-built column for the same value still issues its own query — proving no shared/static state between two "import runs").
- `applyNumber()`'s strict `^-?\d+(\.\d+)?$` regex rejects thousands-separated (`"1,000"`) and Persian-decimal-separator (`٫`) input — intentional (no silent reinterpretation of ambiguous formats), but not documented in the accordion guide.
- Fallback closures can read sibling columns already resolved earlier in the SAME `importColumns()` array (e.g. `cost_center_id`'s fallback reads `$ctx->record->department_id`, `department_id`'s fallback reads `$ctx->record->requester?->department_id`) — this depends on array declaration order matching dependency order. `ApplyColumnFallbacks` iterates `$context->columns` in the order the module declared them; reordering a module's `importColumns()` array without checking these dependencies would silently break the chain.
- ~~CSV formula-injection escaping incomplete on `creator`/`updater` columns~~ — **fixed 2026-10-05.** Found by a `claude-reviewer` pass during the Shipment/Custom audit: every converted exporter's `creator`/`updater` columns read `User::name` (genuinely user-settable free text) completely unescaped, while every other free-text column already went through `plainText()`/`escapeCsvFormula()`. Swept across all 7 affected exporters at once (`BankProfile`, `Payment`, `PurchaseOrder`, `Correspondence`, `Shipment`, `Custom`, `Department`) — each now routes `$record->creator?->name`/`$record->updater?->name` through its own existing `plainText()` helper, same as every other free-text column. `PurchaseRequest`/`ProformaInvoice`/`RegisteredOrder`'s exporters don't export `creator`/`updater` at all, so there was nothing to fix there. One new test per file (7 total, `test_exporter_escapes_formula_injection_in_creator_and_updater_names` / the `ExportDepartmentsTest` equivalent) locks this in; the 4 later mirror job-test files (`ExportPurchaseOrders`/`ExportPayments`/`ExportShipments`/`ExportCustoms`, added 2026-10-06) include their own equivalent from birth. **Lesson for any future exporter:** when a column reads a free-text attribute off a relation (not just the record's own column), it needs the same escaping as a direct column — `creator`/`updater` are the standing example, not a one-off.
- ~~A strict `match()` column on a `NOT NULL` FK validates a non-blank unresolved value correctly, but a BLANK value on a required column passes validation and only fails later as a raw, untranslated SQL NOT-NULL violation at insert~~ — **fixed 2026-10-05.** `CustomImporter`'s `shipment_id` was the instance that surfaced it. **The prior write-up of this gap was wrong about the mechanism**: no new `ImportColumnDefinition` flag was needed — `withFallback($closure, rejectIfStillBlank: true)` was already decoupled from match config (`hasMatchConfig()`/`hasFallback()` are independent booleans, confirmed in "Match and Fallback are NOT mutually exclusive" above) and `ApplyColumnFallbacks`/`RejectMissingManualColumns` already check `hasFallback()`/`rejectIfStillBlank()` with zero awareness of whether the column is also a `match()`/`matchStatus()` column. Chaining the EXISTING `->withFallback(fn () => null, rejectIfStillBlank: true)` onto a strict match column makes a blank value on a NEW record reject cleanly through the exact same path `manualSet()` already uses — proven directly against `CustomImporter::shipment_id` before any fix shipped. Swept every importer's NOT-NULL FK/match column against its real migration (not guessed) and fixed the ones with no blank-handling at all: `CustomImporter::shipment_id`, `BankProfileImporter::registered_order_id`, `ShipmentImporter::registered_order_id`/`company_id`, `RegisteredOrderImporter::seller_id`/`buyer_id` all got `->withFallback(fn () => null, rejectIfStillBlank: true)` added. A second, narrower edge case in the same class of bug: `ShipmentImporter`/`RegisteredOrderImporter`/`PurchaseOrderImporter`'s `status_id` already had a real fallback (`Status::findBy(...)?->id`) but no `rejectIfStillBlank`, so if the looked-up status name ever stopped existing, the fallback would resolve to `null` and still crash raw at insert — all three now pass `rejectIfStillBlank: true` too. See the taxonomy entry below for the standing rule.
