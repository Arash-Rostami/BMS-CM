# Calendar Rules subsystem — pattern & tracing guide

Lead-owned reference for `app/Services/Calendar/`. Written during review from code that was read and tested, then extended slice by slice. Governing spec: `calendar-rules-build-plan.md` (project root) — sections 8 and 9 there override older text. Where this file and a domain doc conflict, the domain doc wins.

Status: services (modules, resolver, range, presenter, engine, router, alerts, activity), jobs, observers and the notification renderer are documented. Resource, widgets and landing tab are appended as each is reviewed.

## 1. Data flow (target design)

```
CalendarRule (user-defined)  ──engine──▶  CalendarHit (one row per matched record)  ──▶ grid / agenda / day table / alerts / activity
   filters (Filament RuleBuilder JSON)        unique (rule, subject_type, subject_id)
   date_path + day_shift                      event_date, alerts_sent, overdue_count
```

- A rule picks one of the 8 operational modules (`CalendarModules`), a condition tree, a date path (+ day shift), lead times, type (heads-up | action), color, visibility.
- The calendar and every list read ONLY prepared `calendar_hits`; nothing evaluates rules at read time.
- Read access is gated by the SUBJECT module's `{model}.view` permission for every user, admins included (no admin bypass on modules). Admins differ only on rules: they see every rule and may edit any rule.

## 3. CalendarPathResolver contract and gotchas

- `columns($class)`: typed (`date|number|boolean|text`) from `Schema::getColumns`, cached 1 day under `calendar_columns:{table}`; blocked columns `password`, `remember_token`, `deleted_at`.
- `relations($class)`: public zero-argument methods declared under `app/Models` (traits count as the composing class) whose DECLARED return type is a `Relation` subclass; cached 1 day under `calendar_relations:{class}`. A method without a return type hint is invisible — that is the exposure contract ("a model exposes only what it declares"). `MorphTo`, every `HasManyThrough`/`HasOneThrough` and every method marked `#[Indirect]` (`App\Models\Attributes\Indirect`, the convenience shortcuts over pivots/morphs, see `modelsPattern.md` §4b) are excluded, so they never appear in `relations()`, `tableOptions()`, paths or routing. Each candidate relation method is invoked once to read its related class.
- `validatePath($subject, $path)`: the last segment must be a column; every earlier segment must be a declared relation; revisiting a class already on the path is a cycle and is rejected; depth is capped by `config('calendar.max_path_depth')` (6). Re-validated server-side on save (a tampered payload cannot persist a bad path).
- Matching needs no hand-written SQL: `QueryBuilderScope::make($rules, $constraints)` turns a dotted constraint attribute into a nested `whereHas`, so relation depth is unlimited.
- `datePathOptions`: date columns reachable only through single-valued hops (BelongsTo / HasOne / MorphOne) — a date on a HasMany is ambiguous. `deleted_at` plus the user session dates (`last_log_in`, `last_log_out`, `email_verified_at`) are excluded everywhere, and `created_at`/`updated_at` are excluded on linked records but offered on the rule module's OWN dates (`OWN_AUDIT_DATE_COLUMNS`) — all in ONE place (`SYSTEM_DATE_COLUMNS`, via `dateColumns()`), so the picker, the engine's preview validation and the grouped list agree; date options take no extra paths (every single-valued related date is already listed). `groupedDatePathOptions` is the form's view: group heading = owning module (`CalendarModules::label`; a second path to the same module gets the relation path appended), option = `<Field> — <meaning>` from `lang resources/calendarRule/strings.date_hints.{table}.{column}` (fallback: field name only; a hint equal to the label is dropped). Option keys are the stored `date_path`; Filament flattens groups for its `in` rule. `describePath` feeds the live helper text (meaning + module).
- "Table" picker (tab 2, above the condition builder; not stored, `dehydrated(false)`, live): `tableOptions($subject, ?User)` returns `['direct' => [...], 'far' => [...]]` - the rule module itself first (key `OWN_TABLE`), then every table reachable in at most 2 hops (`TABLE_HOPS`; nothing deeper), each class once through its shortest route (breadth-first, so a table is never listed twice), keyed by relation path. `direct` = self + 1 hop (label = `PermissionLabeler::getEntityLabel`, via `CalendarModules::label`), `far` = 2 hops, label `<Table> (via <Table>)` (`form.linked_via`). Skipped: `TECHNICAL_RELATIONS`, `AUDIT_RELATIONS` (creator/updater), `*Exclusive` scope duplicates, every relation into `User` (so nothing is reached through a user), unviewable modules (`.view` check per hop). Each group is sorted and capped at `OPTION_LIMIT`; memoised per (subject, user). Saved legacy paths (any depth, any module the user may view) stay valid through `validateRelationPath`/`relationViewable` and keep rendering through the constraint set - the picker only decides what the "Add condition" list offers. `usedPaths($subject, $filters)` = relation paths implied by the DOTTED leaf types of a saved tree (an undotted type is an own column or own FK selector, never a relation), `[]` on malformed input; `leafNames($filters)` lists the leaf types.
- Foreign-key selectors on linked tables: `addRelationConstraints` swaps every FK column of a linked class for a `RelationshipConstraint` named `<path>.<relation>` (e.g. `purchaseRequests.requester`; label `<Module> › <Field>`, or the chain label for a User/repeated class), exactly like the own-table selectors, options by lazy search on the title column. Skipped: creator/updater audit relations, FKs whose target is not viewable, relations that would form a cycle or exceed the depth cap. Such a leaf is a relation path whose last hop is a BelongsTo (`selectorParent`): `relationPathsFor`/`usedPaths` derive the PARENT table path from it (never the target table, which would drag in all of its columns), `classesForType` returns the hop classes, `settingLabel` resolves ids to names. The router already watches the FK on that hop (`watchTerminalRelation`), so changing the linked record's FK re-evaluates the subject. Engine/no-user calls still keep the plain `*_id` column next to the selector so legacy leaves validate.
- Selector operator caveat: `relationshipConstraint()` sets the operator's `baseQuery()` to its own `apply()`; the vendor default (`whereHas` around `apply`, because the constraint attribute is dotted) nests the relation twice and never matched. Own-table selectors had the same latent bug and now sync correctly.
- Selector names: the relationship selector labels by the locale display column (`NameSearch::display`: fa name-first, others english_name-first, then `SCANNABLE_IDENTIFIER`/`title`/`code`) and, when the related table has 2+ name-like columns, searches ALL of them via `getSearchResultsUsing` (LIKE-escaped, limit 50); `settingLabel`/vendor summary use the same display column. Stored values stay ids.
- `CalendarPathResolver` is a container singleton (`AppServiceProvider::register()`): the memos survive the ~8 resolutions per Livewire render. Queue workers hold it until restart (deploy restarts them, same as the column/relation caches).
- Label resolution (`columnLabel`/`relationLabel`): current-locale own-module `strings.form.*` then `strings.table.*` key, current-locale curated map `resources/general/strings.columns.*` / `.relations.*`, then the same two with locale fallback, then `humanize()`; a label is cut at ` — ` (long hint-style form strings). Every column/relation reachable from the 8 modules and their 1-hop links has a curated fa/fr entry; `CalendarSubsystemTest` fails if a fa/fr label equals the English headline of its raw name (acronym allowlist). Chain separator is `›` (direction neutral), never `→`.
- Technical columns (`id`, `path`, `*_id`, `*_type`) are hidden from the condition builder when a user is passed to `constraintsFor`, unless a saved leaf already uses them (`$keep` = `leafNames`); FKs with a relationship selector stay as the selector. The engine (no user) still sees everything.
- `sentence($subject, $extraPaths, $rules)` renders the plain-language condition text from the vendor operators' localised `getSummary()` (AND/OR words from lang); the form no longer shows it; `summaries()` (infolist) reuses the same parts per top-level node, so both are localized and render dates through the calendar toggle. `AdaptiveDateConstraint` (built by `typedConstraint` for date columns) swaps the vendor After/Before/Is-date operators for subclasses with Jalali-aware pickers and `adaptiveDate()` summaries (relative mode prints the resolved date). `isMonth`/`isYear` stay Gregorian by design (the DB `whereMonth`/`whereYear` are Gregorian). Vendor strings missing in fa/fr are filled by `lang/vendor/filament-query-builder/{fa,fr}/query-builder.php`; `CalendarRuleResourceTest` fails if the fa/fr sentence contains an English word from the en rendering.
- `constraintsFor($subject, $extraPaths, ?User, $keep)` = the module's OWN columns (foreign keys swapped for relationship selectors) + every column of each given relation path. EVERY label is `<Table name> › <Field name>` (table = `CalendarModules::label` of the owning class, field = `columnLabel`), so each condition row reads module, field, operator, value; a `User` table or a class reached by two paths keeps the relation-chain label (`pathLabel`, e.g. `Requester › Name`) because the module name alone would be ambiguous. `relationPathsFor($subject, $extraPaths, $filters)` is the single normaliser: it unions the given paths with the relations implied by dotted leaf types and accepts legacy column-shaped paths (`creator.name` becomes `creator`), so rules saved before the picker model still validate and sync (`constraintsForRule` uses it). Labels: translated key first, else `humanize()` so no raw snake_case or camelCase reaches the UI.
- `validatePath` is strict: an empty path, a leading or trailing dot, or a double dot is rejected (no silent segment dropping), because the raw string is stored and used as the constraint name.
- Sensitive columns: `password`, `remember_token`, `deleted_at` and `two_factor_*` everywhere; on `User` also `ip`, `phone`, `email`, `settings`, `image`, `role` (reachable through requester/approver/creator relations otherwise).
- User-aware gating: `constraintsFor($subject, $extraPaths, ?User $user)` and `tableOptions(..., ?User $user)` skip foreign-key selectors, related columns and path hops whose related model the user lacks `.view` on. The ENGINE always calls them with no user (it must resolve every stored rule); only form and picker code passes the acting user. A rule stored through a swapped foreign key keeps the relation name as its constraint name — never rename it per user.
- Relations must declare a Relation return type to be exposed. The pipeline links (`registeredOrders`, `purchaseRequests`, `proformaInvoices`, `purchaseOrders`, `customs`) are typed for that reason; any new relation method needs a return type or the calendar cannot filter through it.
- `isAppDeclared` compares against `realpath(app_path('Models'))` (symlinked release directories).

## 4. Rule model facts (Steps 1-2)

- `calendar_rules` (SoftDeletes) and `calendar_hits` (derived: no SoftDeletes, no UserStamps). `activity_log` comes from `spatie/laravel-activitylog`, shipped here as ONE merged migration (the package's three stubs folded into one create file); retention set effectively unlimited.
- `CalendarRule::scopeVisibleTo`: admins see all rules; others see `everyone`, their own, or rules whose `shared_user_ids` contains them — the shared list counts ONLY when `visibility = users` (a stale list must not leak after switching to `me`/`everyone`). `shared_user_ids` is stored as ints through `App\Models\Casts\SharedUserIdsCast`; membership is queried in both int and string JSON forms.
- `HasFingerprint`: `conditions_hash` = subject + canonical filters + date path; `fingerprint` additionally includes `day_shift` and `type`. Canonicalization ignores the RuleBuilder's random item keys and the order of conditions. Exact duplicate = same `fingerprint` (blocked); near duplicate = same `conditions_hash` (warn + merge lead times; the merge target is limited to the user's own rules, any rule for admins, and needs `calendar_rule.edit`). The rule form re-validates `extra_paths` and every filter leaf server-side against the acting user's viewable modules (`constraintsFor(..., $user)`), and Duplicate always starts `me`, unshared. `day_shift` is cast to int so null and 0 hash alike.
- `CalendarHit::scopeVisibleTo`: always `whereIn('subject_type', CalendarModules::viewableBy($user))` AND the rule must be visible to the user. `scopeOverdue`: Action-required rules only, `event_date < today()` — a hit dated today is NOT overdue.
- Time rule: every date comparison uses `today()` / `startOfDay()`, never `now()` (gotchasPattern midnight boundary).
- Migration conventions applied: the stamp pair `user_id` / `updated_by_id` is unconstrained and carries the named indexes `idx_calendar_rules_user_id` / `idx_calendar_rules_updated_by_id` (see `modelsPattern.md` §9).
- New folder `app/Models/Casts/` holds custom casts (`modelsPattern.md` §13).

## 6. Sync (CalendarEngine) rules

- `syncRule(CalendarRule): bool` takes `Cache::lock('calendar_rule_sync:{id}', 900)` and refreshes it per chunk; a busy lock returns false and the job retries in 60 s (an edit made during a running sync is never dropped).
- Inactive, soft-deleted or unknown-subject rules purge their hits. A rule with an invalid stored filter (unknown leaf type, unknown operator, missing type, malformed OR block or non-array leaf) is INVALID: hits purged, one `rule_invalid` activity row (only when the purge deleted hits or the problem set changed), never "match everything". `filterProblems()` is memoized per rule id + `updated_at`; `syncSubject` uses the same check.
- Scan: `chunkById` (`calendar.sync_chunk`, 500), one transaction per chunk, upsert keyed `(rule, subject_type, subject_id)`. A changed `event_date` resets `alerts_sent` and `overdue_count` and logs `date_changed`. The comparison uses the raw DB value, never a cast one.
- Sweep: after the scan, hits whose subject id is not in the matched id set are deleted in chunks (never a count-sized `whereNotIn` — MySQL rejects more than 65,535 placeholders). Hits touched at or after the scan start survive one more run (a fresh hit from `syncSubject` is never lost; a stale hit is cleared at most one run late).
- Defensive typing: `leafProblems()` only trusts an item of the constraint list when it is a real `Constraint`; anything else (for example a closure handed in by a caller) is reported as an unknown type instead of a fatal error.
- Activity is transitions only (matched, date_changed, cleared), written with bulk inserts, never "still matches".
- `preview(User, ...)` requires the subject in `CalendarModules::viewableBy($user)` and validates the payload shape; failures are `ValidationException`, never a 500. An empty condition tree means all records of the module.
- Heads-up hits past their date stay in the table; the read side (calendar widgets) excludes them.

## 7. Routing (CalendarRouter)

- `touch($model, $event)` is the observers' only entry point. It exits at once for suspended runs, `CalendarRule`, `CalendarHit`, `Pivot`, classes outside the routing map, and updates that touch no watched column (created, deleted, restored and forceDeleted are always structural).
- Each rule stores `watched_columns` `{FQCN: [column, ...]}`: filter columns, the date column, foreign keys of every hop and `deleted_at`. The routing map is a static rebuilt when the cached version stamp (`calendar_routes_version`, a uuid bumped by `CalendarRuleObserver`) changes — workers running for a long time pick up rule edits.
- A change on a related model resolves the affected subject ids through a reverse `whereHas` (soft-deleted related rows included), unioned across every path that reaches the class, then dispatches `SyncCalendarSubject` per id. Zero subjects means nothing to do. A path that cannot be expressed, or more than 50 subjects, dispatches ONE debounced `SyncCalendarRule` instead.
- Known limitation: re-parenting a to-many related row (for example an item moved to another request) resyncs only the new parent; the old parent is corrected by the 02:00 rebuild. Queries that skip model events (`update()`, `upsert()`) are only caught by that rebuild.
- `CalendarRouter::suspended(fn)` pauses routing (imports, bulk jobs — `ImportDefaults::__invoke` wraps every imported row in it, then queues one delayed `SyncCalendarRule` per active rule of the importer's model; the job is unique-until-processing so a 2,000-row import queues a handful) and restores the previous value; `CalendarRouter::flushRoutes()` resets the static and bumps the version stamp.

## 8. Alerts and activity

- `CalendarAlerts::sendDue($today)` fans out one job per active rule. Per rule and day each recipient gets ONE notification merging lead, on-day and overdue items (first three labels + "+N"). Recipients are `CalendarRule::recipients()` (module `.view`, active users, no admin bypass).
- Zero recipients: nothing is sent, marked or logged, so a user granted access later still gets the alert.
- Visibility has four mutually exclusive values (`Visibility`: me | everyone | users | roles). `roles` stores `shared_role_ids` (same `SharedUserIdsCast`, nulled on save for any other visibility) and its audience is active users holding a chosen role AND the module `.view` permission; `visibleTo` matches a viewer's own role ids (`$user->roles`, one query) via `whereJsonContains`, owner/admin always see. `recipients()` is the audience per value (me = owner, users = owner + shared, roles = role members only, so the owner of a roles rule is alerted only if he holds a role; everyone = all), always intersected with module `.view` and not-inactive, no admin bypass. Duplicate keeps `roles` + its role list, every other source starts `me`.
- Outside emails (`notify_emails`, a column of the create-table migration `2026_10_08_100001`, max 10, 254 chars each): mail-only, sent through `Notification::route('mail', $email)` as an `AnonymousNotifiable` (`via()` forces `mail`; greeting/outro have anonymous keys; no Open link, so no record URL leaves the app). Only used when the channel is email/all (field auto-hides and clears otherwise; the model `saving` hook nulls them for in-app rules). `OutsideEmailsCast` lowercases, trims, drops anything with whitespace/quotes/angle brackets/CRLF or failing `FILTER_VALIDATE_EMAIL`, dedupes and caps, on read and write. The form rejects repeats and any address already in the audience (`recipients()` of a transient rule). Idempotency uses cache key `calendar_alert_mail:{rule}:{date}:e{sha1(email)}` (set after the send, like the user key); at send time an address equal to a recipient's email is dropped. Addresses never reach the activity log, the calendar or other users' notifications; the infolist, duplicate and export show them only to users who may edit the rule (others see a count).
- Sending is idempotent per recipient (an existing notification row with the same `rule_id` and `alert_date` is skipped); marking happens in one transaction that re-selects the due hits with `lockForUpdate` and re-checks `event_date`, so a concurrent re-arm wins. `SendCalendarRuleAlerts` is unique per rule and day.
- Channel: `calendar_rules.notification_type` (`in_app` default, `email`, `all`) reuses `HasNotificationChannel` and the Notification Settings labels. `CalendarAlertNotification::via()` maps it to `database`/`mail`/both (unknown value falls back to `config('calendar.channels')`); `toMail()` lists the first three item labels plus "+N more" and an Open link built as `config('app.url')` + the relative path of the open URL. Mail strings are `resources/calendarRule/strings.mail.*` (en/fa/fr), resolved at send time in the worker's locale, exactly like `ModelEventEmail` (no per-user locale exists). The `notifications` table only records database sends, so a rule that does not send in-app (email-only) is deduped by the cache key `calendar_alert_mail:{rule}:{date}:{user}` (2 days): `pendingRecipients` skips users whose key exists and `deliver` sets it only AFTER that user's send returned (a failed SMTP send leaves no key, so the retry still reaches them; `cache:clear` wipes the keys, so a same-day rerun after a cache clear may re-mail); `all` still uses the database rows. Sends are per recipient so a mid-batch failure never guards away the users not yet sent.
- Overdue (Action-required only): first alert at event_date + 1, then every 7 days, at most `calendar.max_overdue_alerts` (3). A hit dated today is not overdue.
- The notification stores translation keys + params, not text; `App\Livewire\CalendarDatabaseNotifications` renders them in the viewer's locale and passes vendor-shaped payloads through untouched. Malformed payloads fail closed.
- Activity descriptions are keys rendered from `resources/calendarRule/strings.activity.{event}` at read time; `forRecord()` reads at most 100 rows through `idx_activity_log_subject_created`.
- Jobs: queue from `config('calendar.queue')` (set in each constructor; env `CALENDAR_QUEUE`, default `default`, so the standard workers pick the jobs up with no special flag), sync jobs `ShouldBeUniqueUntilProcessing` (the lock frees when processing starts, so an edit made during a running sync queues a fresh job instead of being dropped) with `tries=3` and backoff, no swallowing try/catch. `ExportCalendarHits` flushes the per-process `CalendarHit::visibleRuleIds` memo first, because a long-lived worker would otherwise reuse a stale rule-visibility list.
- `SyncCalendarRule` is bounded by time, not attempts: `retryUntil()` 30 minutes plus `maxExceptions = 3`. A busy rule lock calls `release(60)`, and a release consumes a try, so a fixed `tries` would fail a queued follow-up while a long sync runs.
- `CalendarRuleObserver::saved` ignores a save that changed nothing (no `rule_updated` row, no version bump, no sync); on the instance that was just created `wasRecentlyCreated` is still true, so test with a fresh instance.
- The scheduler entries use `withoutOverlapping(60)` so a dead scheduler process cannot hold the day's mutex for 24 hours.
- Form-side gating (steps 7-8 review): `datePathOptions($subject, $extraPaths, ?User $user)` hides dates behind modules the user cannot view and an extra path must have every hop viewable; the exact-duplicate lookup is scoped to `visibleTo($user)` (blocking against a private rule the user cannot open would leak its existence); merge candidates are the user's own rules (any rule for admins) and exclude the edited record; the View modal uses `listWithLineBreaks()` (there is no `listWithSummary`). The infolist summary shows chosen related-record labels (for example company names) to any viewer of a shared rule: rule metadata, accepted. The View modal also shows the hits count (`viewHitsCount()` badge, gray at 0 / success otherwise — the table column and the infolist entry share the `hits_count` lang keys). `canEdit`/`getEditAuthorizationResponse` fail CLOSED for any record that is not a `CalendarRule` — Filament evaluates resource authorization against whatever model a modal is holding, so a non-rule instance must deny, never assume instanceof passes.
- Observers: `CalendarRuleObserver` (fingerprints and `watched_columns` on saving; activity, version bump and a sync on saved (immediate for a NEW rule, 120 s debounced for edits — `wasRecentlyCreated` is true for the whole life of an instance, so tests must edit via `fresh()`); immediate purge on delete) and `CalendarTouchObserver` (explicit class list in `AppServiceProvider`, no second filesystem scan).

## 9. Dashboard calendar tab (step 9)

- First tab of the Dashboard (`Dashboard::TABS`, with a per-tab `columns`/`spans` map; other tabs keep the 2-column default). Two widgets: `CalendarGridWidget` (month grid + agenda) and `CalendarDayWidget` (Filament `TableWidget`, the side panel). Both are `$isLazy = false` (a lazy mount would run in the Livewire update request and lose the URL state, and the two widgets would race on the selection event). They talk through the Livewire events `calendar-day-selected` (date, rule, module) and `calendar-toggled` (calendar type flipped; both widgets re-render).
- URL/Livewire state: `cal_date`, `cal_rule`, `cal_module` are `#[Url]` properties typed `mixed` and sanitized in `mount` AND in the `updated*` hooks through `CalendarBoard::sanitize` / `CalendarRange::parseIso`: a typed `?int`/`?string` property crashes on a forged value before `mount` runs, and the client can set public properties at any time. Invalid values fall back to today / no filter, never a 500.
- `CalendarBoard` (Display/) owns the scoped read side: ONE grouped query per month (event_date, rule, count, overdue flag), the day query, legend/filter option lists. Everything goes through `CalendarHit::visibleTo` (module `.view` for everyone, no admin bypass); rule names, legend chips and filter options are limited to rules whose subject module the user can view (a rule name is a hint too). Heads-up hits past their date are excluded by `CalendarHit::notPastHeadsUp`; Action-required stay and are flagged overdue only when `event_date < today()`.
- Day table: grouped by module, ordered by the LOCALIZED label (`orderQueryUsing` with `FIELD(subject_type, ...)` built from the sorted labels; ordering by the class name would not be alphabetical in fa/fr); row click opens the record (a hit whose record was deleted renders without a link); export bulk action dispatches `ExportCalendarHits`, which re-applies `visibleTo`.
- Markup traps found in review: never use `range(1, $n)` as a repeat count (`range(1, 0)` has two items; use `@for`); blade `@include`d partials do not inherit Livewire computed properties; the Alpine `x-data` scope must wrap both the header and the grid/agenda; a `TextColumn` skips `formatStateUsing` for a blank raw state, so use `->state()`.
- Tiles (`.cal-*` in `fi-custom.css`): raised rounded cells; today tinted, selected filled, +N badge, up to 3 rule-colour dots, red ring + alert icon for overdue days; below `md` the grid is replaced by the day-grouped agenda. No maximize toggle, no help modal, no "New rule" button on the tab. Since 2026-10-10 the agenda items link to their records and the legend chips are click-to-filter buttons (§13).

## 10. Activity button and landing "Needs attention" tab (checkpoint 10+12)

- **Activity button** (`App\Filament\Actions\CalendarActivityAction`, rendered in the calendar GRID WIDGET toolbar, not in the Dashboard header: `CalendarGridWidget` implements `HasActions` + `HasSchemas`, exposes `calendarActivityAction()` and the view includes `<x-filament-actions::modals />`; `Dashboard::getHeaderActions()` returns `[]` so the other tabs have no Activity button): module select (`CalendarModules::viewableBy`) -> searchable record select (module identifier, escaped LIKE, max 25; soft-deleted records of models that use `SoftDeletes` are included and tagged with a localized "(deleted)" suffix, module `.view` still required) -> "show all" toggle -> history. All data paths (`searchRecords`, `history`, `recordFor`) take the acting user and fail closed: forged class strings, unviewable modules, bad ids and a null user return nothing. Typed Select callbacks must accept `mixed` (forged Livewire state).
- **History is viewer-scoped.** `CalendarActivity::forViewer($record, $user, $all)` limits the rows to events of rules the viewer can see (`CalendarRule::visibleTo`): a private rule leaves no trace (rule name, label, dates) in the default tier, "show all", or the seen-event synthesis. The filter is applied in SQL on `properties.rule_id` BEFORE the 100-row cap so hidden rows cannot crowd out visible ones; `forRecord($record, $all, ?array $ruleIds)` keeps `null` = unrestricted for internal callers. A soft-deleted rule's events disappear (fail closed); a shared rule that becomes private hides its history (current visibility wins). Row text is rendered at READ time from `strings.activity.{event}`; stored properties are cast through scalar guards, unknown events are dropped, dates go through `adaptiveDate`, the output is escaped.
- **Landing tab** (`App\Livewire\LandingPage\Attention`, view `livewire/landing-page/attention.blade.php`, inserted right after the Search tab in `landing-page/header.blade.php` (before the right-aligned Features tab), gated by `$attentionVisible` = the user can view at least one calendar module): data comes from `CalendarEngine::attention(User, limit = 10)`: ONE query through `CalendarHit::visibleTo` + `notPastHeadsUp`, eager `rule` and `subject` (a morph eager load is one query per module type; a deleted record has a null subject and renders without a link), window = overdue Action-required OR event_date in [today, today + 7], ordered by event_date; no viewable module means zero queries and the tab is hidden. Render-only eager Livewire per the landing-page rules (no wire:model, no #[Lazy]). Since 2026-10-10 the tab also shows the true total via `CalendarBoard::attentionCount()` (mirroring this window exactly — see §13) and a "+N more" tail when the 10-row cap truncates.
- Open: `attention()` lives in the write-side engine by plan; `Display/CalendarBoard` (the scoped read-side class) would be the more natural home.

## 12. Selector rules and legacy handling (predefined values)

- `CalendarPathResolver::typedConstraint()` builds a multiple searchable `SelectConstraint` for a text column when `PredefinedOptions::optionsFor($class, $column)` is non-null; operators 'is' (any of / none of via inverse) and 'isFilled' only if the column is nullable. Labels come from the options map in the current locale, so `summaries()`/`sentence()` render selected options by label. Booleans keep `BooleanConstraint`, FK relation selectors stay single `IsRelatedToOperator` (a multi FK selector would change the stored `value` -> `values` shape).
- Engine and `CalendarFilterTree` need no change: validity is `operatorExists()` against the constraint built for that rule, and `QueryBuilderScope` applies `whereIn`/`whereNotIn` from `settings.values`.
- **Legacy:** `constraintsFor(..., $keep, $textLeaves)`; `textLeafNames($filters)` returns the paths whose saved leaves use a text operator (contains/equals/startsWith/endsWith). Those paths keep the `TextConstraint` for that rule (`constraintsForRule`, `sentence`, the builder via `filterConstraints`) so rules like the saved `transport_mode contains cfr` still validate, sync and display; removing the legacy leaf lets the path become a Select again. A second condition on the same path in such a rule is therefore still offered as text.
- **Lookup tables:** every non-technical column of a chosen table is offered (only `id`, `path`, `*_id`, `*_type` and blocked columns are hidden; FKs appear as record selectors). For the reference models in `PredefinedOptions::LOOKUP_MODELS` (Bank, Category, Company, Currency, Department, Product, Status - the only switch) reached through a BelongsTo, the name-like columns (`NameSearch::columns()`: name, english_name, code, title) build a multi-select `SelectConstraint` of the table's existing distinct values (`existingValuesConstraint`: 300 loaded, LIKE search beyond, label = value); saved leaves with a text operator stay `TextConstraint` (`textLeafNames`), so `costCenter.name contains ...` stays valid. Operational identifier columns stay text.
- **One entry per relation path:** `reachableTables` dedupes a table only across hops (a farther hop never repeats a nearer table). Within one hop, every relation reaching the same table is its own entry (PurchaseRequest: `department` and `costCenter`); labels use the relation label (`strings.form.*` / `general.relations.*`) and fall back to `<Table> — <relation>` only when two labels collide. A table reached by one relation keeps its plain table name. Leaf names are path-prefixed (`department.name` vs `costCenter.name`).
- **Both-name labels:** `NamedIsRelatedToOperator` (Calendar FK selectors) and `NameSearch::label()/labels()/options()` (also Notification FK selects via `ModelInspector::relatedLabels`) label records `<name> — <english_name>` (fa: name first; others: english first; identical or single names are not repeated); search still matches every `NameSearch::columns()` column.
- **Input priority:** table/FK -> enum -> localized option sources -> boolean -> stored-values scan -> free text (`modelsPattern.md` section 11).

## 13. Resource UX wave (2026-10-10)

- **Scoped hits aggregates:** `CalendarRuleResource::getEloquentQuery()` counts/mins hits through a private `scopedHits()` helper applying `CalendarHit::visibleTo(auth()->user())` + `notPastHeadsUp()` — the list badge, the infolist `hits_count` entry, and the `Next due` column all show only what the viewer's calendar shows. An unscoped `withCount('hits')` would silently count past heads-up events and hits in modules the viewer cannot open (fixed live bug — the badge lied).
- **Next due column:** `withMin(['hits' => scopedHits(...)], 'event_date')`; `showNextDue()` renders it via `adaptiveDate()`, danger red when the date is past, warning amber within 7 days, blank when no upcoming hit.
- **"What it watches" column:** `showWatches()` is `isToggledHiddenByDefault()` — zero list noise until the user opts in via the column toggle; `getStateUsing` reuses the View modal's own rendering (`datePathOptions` label + `CalendarPathResolver::summaries()`), never a fork; per-row cost only when toggled on, bounded by page size.
- **"See on calendar" action:** `getSeeOnCalendarAction()` links to `Dashboard::getUrl(['cal_rule' => $record->id])` — the grid's `#[Url(as: 'cal_rule')]` param is the whole contract; placed after ViewAction.
- **Agenda links:** `CalendarBoard::agendaHits()` eager-loads `subject`; `CalendarPresenter::withRules()` takes a relations array (`agendaDays` passes `['rule','subject']`); `overdueFirst()` adds a `url` key (null for a deleted subject → the blade renders plain text, never a dead link). Fixes the mobile dead-end (below `md` the agenda IS the calendar).
- **Legend chips filter:** the grid legend's chips are `wire:click="toggleRule(...)"` buttons; `CalendarGridWidget::toggleRule()` reuses the `updatedRuleId()` sanitize + emit path (a foreign/private rule id sanitizes to null — fails closed), the active chip is tinted via inline `color-mix` of the existing `--cal-color-*` vars (no new CSS classes), clicking the active chip clears the filter.
- **Attention total:** `CalendarBoard::attentionCount()` + `attentionWindow()` (read side only; the write-side engine untouched) mirror `CalendarEngine::attention()`'s window exactly (overdue Action-required OR event_date in [today, today+7], `visibleTo` + `notPastHeadsUp`); `Attention` shows the true total and a "+N more" tail when the 10-row cap truncates. A window drift between the two would make the "+N" lie — `LandingPageAttentionTest` locks them together.
