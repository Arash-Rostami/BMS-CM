Four families of job class; the import/export families serve Purchase Request's bulk import/export (`app/Filament/filamentPattern.md` §1.8a/§1.8b documents the full system these belong to — read that first), the calendar family serves the calendar subsystem:

- `App\Jobs\ImportCsv extends Filament\Actions\Imports\Jobs\ImportCsv` — the plain, non-grouped import job, wired via `App\Filament\Actions\ImportAction`. Purchase Request/Proforma Invoice/Registered Order all have item rows and use the grouped variant below instead; Bank Profile has no item rows at all, so `BankProfileImporter` was the first consumer of this plain job; Department (2026-09-26) is the second — same flat shape; Currency is the third (create-only, no `SCANNABLE_IDENTIFIER` — see `app/Services/Imports/importsPattern.md`'s "Currency" section).
- `App\Jobs\ImportGroupedCsv extends Filament\Actions\Imports\Jobs\ImportCsv` — iterates parent+item GROUPS instead of individual rows, full group-atomic rollback on any item failure. Used by Purchase Request/Proforma Invoice/Registered Order, dispatched by `App\Filament\Actions\GroupedImportAction`.
- `App\Jobs\Export{PurchaseRequests,ProformaInvoices,RegisteredOrders,PurchaseOrders,BankProfiles,Departments,Correspondences,Payments,Shipments,Customs,Products,Categories,Banks,Statuses,Currencies,Companies,NotificationSettings,Roles,Permissions,Targets,Users}` — one per module with a bulk export action; each writes a CSV to `storage/app/exports/{user}/{file}.csv` via its own `{Module}Exporter::write()`, then notifies the user with a signed download link (success) or a generic error notification (failure, real exception goes to `report()`). `Product` (2026-10-06) is the third flat (non-grouped) `ImportAction`/`ImportCsv` consumer, mirroring Bank Profile/Department's wiring. `Status` gets export only, no importer — it's a shared polymorphic lookup referenced everywhere, and `StatusObserver` invalidates `SmartCacheManager`/`StatusWorkflow` caches on every save, so a bad bulk upload has wide blast radius for unclear benefit. `ExportCompanies` mirrors `ExportDepartments` 1:1 (flat, no item rows). `ExportNotificationSettings` (2026-10-07) mirrors `ExportBanks` 1:1 as well (no importer — per-user config). `ExportRoles`/`ExportPermissions` (2026-10-07, QA-driven — neither module had export before) and `ExportTargets` (2026-10-07, `TargetExporter` converted from a native `ExportColumn`-based Exporter to this shared shape in the same pass) all mirror `ExportBanks` 1:1; none of these three get an importer (settled policy, see `app/Services/Imports/importsPattern.md` §4). `ExportUsers` (2026-10-07) was the last holdout — `UserExporter` converted from the native `ExportColumn`-based Exporter to this shared shape, closing out the parked worktree branch; no importer (settled policy — bulk account creation touches auth/password/role assignment).

- `App\Jobs\{SyncCalendarRule, SyncCalendarSubject, SendCalendarRuleAlerts, SendCalendarAlerts, RebuildCalendarHits}` — the calendar subsystem's queue jobs (2026-10-08), all read their queue from `config('calendar.queue')` (env `CALENDAR_QUEUE`, default `default`, so the standard workers pick them up with no special flag; set the env and add that queue to one worker only if isolation from imports/exports is ever wanted). `SendCalendarAlerts` (scheduled daily 07:00, `withoutOverlapping(60)` so a dead scheduler cannot hold the mutex for the default 24 hours) fans out one `SendCalendarRuleAlerts` per active rule; `RebuildCalendarHits` (daily 02:00) re-dispatches `SyncCalendarRule` per active rule as the catch-up for event-less query-builder writes. The two sync jobs implement `ShouldBeUniqueUntilProcessing` (debounce queued duplicates, but an edit made while a sync runs must still queue a follow-up) and `SyncCalendarRule` is bounded by `retryUntil()` (30 min) + `maxExceptions = 3` instead of a fixed `tries`, because a busy per-rule lock calls `release(60)` and every release consumes a try. Deliberately NO try/catch on either — a failed schedule run must fail loudly, not vanish (the export jobs' report-and-notify shape is reserved for user-facing exports only). `ExportCalendarHits` is the sixth calendar job and DOES follow the `ExportBanks` 1:1 shape, with one addition: it re-applies `CalendarHit::visibleTo()` to the client-submitted ids — the action's id list is untrusted input, never bind it raw. All schedule entries live in `routes/console.php`.

Test coverage mirrors every job class 1:1 in `tests/Feature/Jobs/` — 26 files: `ImportCsvTest`, `ImportGroupedCsvTest`, `Export{PurchaseRequests,ProformaInvoices,RegisteredOrders,PurchaseOrders,BankProfiles,Departments,Correspondences,Payments,Shipments,Customs,Products,Categories,Banks,Statuses,Currencies,Companies,NotificationSettings,Roles,Permissions,Targets,Users,CalendarHits}Test`, and the calendar pair `SendCalendarAlertsTest`/`RebuildCalendarHitsTest` (the scheduler expressions are asserted straight off `app(Schedule::class)->events()` — `schedule:list`'s Artisan output is empty inside the test env, don't re-chase that). This is a genuine 4th test layer (Resource/Model/Service/Job), not folded into the owning resource's test file, since a Job has its own lifecycle (`middleware()`, `handle()`'s success/failure paths) independent of the Filament Action that dispatches it. See `tests/testPattern.md` §1. The last five (`NotificationSettings`/`Roles`/`Permissions`/`Targets`/`Users`, written 2026-10-08) each copy `ExportBanksTest`'s skeleton and DO cover the failure path (a directory placed at the CSV filename forces the write to fail, `Carbon::setTestNow` pins the name) — the older export tests mostly cover the success path only. Their success assertions check the BOM and the exporter's id header, not row values, because Roles/Permissions names pass through `base_name`/`PermissionLabeler`. `TargetFactory` leaves `targetable_type` null, so Target fixtures use `Target::factory()->forTargetable(...)`.

**Gotcha:** a long-running `queue:work` process caches class code in memory at boot — editing any of these classes (or anything they call) mid-session and testing from the actual running app, without restarting the worker (`php artisan queue:restart`), reproduces a stale-code bug that a fresh `php artisan tinker` invocation of the same job will NOT reproduce. Hit live 2026-09-22 debugging `ExportPurchaseRequests`. The worker caches its boot-time config the same way — after an `.env` change, `php artisan config:clear` alone never reaches a running worker; `queue:restart` is required there too.
