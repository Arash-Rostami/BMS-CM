## Principles
- No DB VIEW. Reports are Eloquent-based Filament pages sharing one abstract `ReportPage` + a `HasReportFilters` trait.
- Reuse the existing schema. A column is added only when no existing data can answer the question.
- Every report: filter bar, summary cards/charts (recomputed from filtered rows), main table with toggleable columns, and a "Records needing attention" table below.
- Every rule that depends on a client definition (stage grouping, "cleared", "in transit", weight net vs gross, include flagged invoices) is a filter with a default, never hard-coded.
- Permissions: 12 dotted `report.*` permissions (5 standard + 7 `report.view_*`). Report 7 is scoped by the user's department (`users.department_id` matched to `purchase_requests.cost_center_id`), reads no financial columns and shows no supplier name.
- Base currency EUR. Rate = latest purchased bank profile (`purchased_equivalent` ÷ `requested_amount`). Different currencies are never summed directly.

## Definitions
- In transit: `exit_date` or `etd` set and not yet arrived. Arrival date is `shipments.eta` (تاریخ ورود); `warehouse_date` is the real-arrival candidate.
- Shipment currency: invoice currency (JSON header) → registered order currency → proforma invoice `main_currency_id`. Computed by one method on Shipment, no column. If the invoice currency is filled and differs from the order's, the shipment is flagged "correct it" and excluded from sums unless the filter includes flagged invoices.
- Customs declared value is derived, not stored: `shipments.grand_total` of `customs.shipment_id`, counted only for cleared customs records (cleared-from-stage is a filter, default «پایان یافته»).
- Report 6 (FX commitments), per registered order in the purchased currency: Purchased = Σ `purchased_equivalent` of bank profiles in «خریداری شده»/«دریافت شده»; Resolved = Σ declared value of cleared customs; Remaining = Purchased − Resolved; Overdue = `commitment_payment_date` < today and Remaining > 0. Invoices cannot be split across several profiles of one order, so resolved/remaining sit at order and company level.

## Schema decisions
- New table `shipment_items` (replaces `items` inside the `commercial_invoice` EAV JSON): id, shipment_id (FK cascade), product_id (nullable, hidden, FK null-on-delete), name (Farsi), english_name (English/Latin), hs_code, origin, quantity, unit, unit_price, total_amount, net_weight, gross_weight (all numbers `decimal(65,5)` + `'decimal:5'`), timestamps, no soft deletes.
- New columns on `shipments`, auto-filled on invoice save, hidden in the form: `total_net_weight`, `total_gross_weight`, `grand_total` (grand total = items subtotal − discount + freight + other charges; the extra parts live only in the invoice header, so it needs a column).
- Invoice tab UI unchanged. Only the backend changes: save writes header + `shipment_items` rows (one transaction), load reads them back, the PDF controller reads them (one shared `loadInvoiceData()`).
- One idempotent production backfill command `shipments:backfill-invoice-items` (`--dry-run`, `--prune`; links products with a multi-step matcher and flags what it cannot match; count-verified; ships in the same deploy as the migration).
- Dropped as unnecessary: `shipments.arrival_date` (use `eta`), `shipments.invoice_currency_id`, `customs.declared_value`, `customs.declared_currency_id`, `users.cost_center_id`, any `is_final` status column (`StatusWorkflow::isTerminal` covers it).
- Dropped by the owner: `registered_order_items.purchase_request_item_id`. Report 7 follows the relation chain purchase request → registered order (`registered_order_purchase_request` pivot) → shipment (`shipments.registered_order_id`) → customs (`customs.shipment_id`), not a direct item link. Only products whose chain reaches customs enter the statistics; the rest are left out. Insight (amount, details) is shown per requester user or department of the purchase request. Product-level amounts read `shipment_items`, which needs `product_id`: new invoices fill it from the proforma items; backfilled rows get it from the backfill's matcher, and a line the matcher cannot match keeps it empty and shows name-level detail only.

## Flagging mechanism
- One check registry, no new table. Each check: key, model, query to find bad records, severity (error/warning), message lang key, fix target (resource edit URL + tab + field). Results cached through `SmartCacheManager`.
- Surfaces: the attention table in each report; a banner and field hint on the record's infolist/edit form; optionally the landing-page «Attention» widget.
- Fix paths: user fix (button to the edit tab, only if `canEdit`); one-click system fix only for unambiguous cases (e.g. empty invoice currency inherits the order's); otherwise show the owner from the latest Audit Log entry. A flag never blocks saving unless decided otherwise; it clears itself when the data is corrected.
- Candidate checks (all from existing columns): missing ETA/ETD for in-transit; missing exchange rate on a purchased profile; ETA before ETD; clearance before arrival; invoice currency ≠ order currency; invoice `grand_total` ≠ recomputed; shipped quantity above ordered; amount/weight/unit-price outliers by percentile; records stuck in a stage past a threshold (`status_histories`).

## Performance and production load (design rules)
- HARD RULE: the main panel must not get slower. Report code runs only on report routes: no global render hooks, no global scopes/observers, no nav count badges or per-request queries for reports, no new eager loads on existing resources, no new work on every page load. Measure query count and time of the Dashboard, a List page and a record View modal before and after the reports ship; any increase on non-report pages blocks release.
- Known panel-wide cost to fix first: the audit Activity tab runs a 50-row query + FK label queries + a count on EVERY record View modal open of the 8 resources, even when the tab is not selected. Make it lazy (load when the tab is selected, or drop the count badge) before adding more load.
- Each report is its own Filament page: nothing loads until the user opens it; within a page the cards, main table and attention table load separately (deferred/lazy), the attention table only when expanded or scrolled to; the table paginates (no unbounded `get()`).
- Use Filament's own lazy loading: build each report block (cards, charts, main table, attention table) as a Filament widget/Livewire component that stays lazy (Filament widgets are lazy by default; only the calendar widgets opt out with `$isLazy = false`), mounted per tab the way the Dashboard's `TABS` const mounts widgets (`widgetsPattern.md`). A tab's blocks then fetch only after the page shell renders, and a heavy block never delays the filters or other tabs. Verify with the browser network tab that a hidden tab's block does not request data until opened (Filament renders all panes, so lazy components, not tab visibility, are what defer the queries).
- Aggregates are computed in SQL (`SUM`/`COUNT`/`GROUP BY`, `withSum`/`withCount`) on Eloquent queries, never by loading rows into PHP; PHP-side grouping (per-currency chains, outlier percentiles) runs only on the already-filtered, paginated or capped set. Eager-load every relation used by a column or badge; no per-row queries.
- Cache expensive blocks with `SmartCacheManager::remember(model, filters, minutes, cb)` keyed by the filter set; invalidate on writes to the involved models (it already hooks model saves); the FX implied-rate lookup (`purchased_equivalent ÷ requested_amount` per profile) is cached once per request/day.
- Indexes: `shipment_items.shipment_id` (FK) and `shipment_items.product_id` (FK) are created by the migration; the existing business-identifier indexes (pending migration `add_business_identifier_indexes`) and FK indexes cover the report joins (`shipments.registered_order_id`, `customs.shipment_id`, pivot tables). Re-check with `EXPLAIN` on the production copy before release; add a composite index only where `EXPLAIN` shows a scan.
- Exports for every report table (main table and the attention table) reuse the app's custom export convention (`filamentPattern.md` §1.8b, `jobsPattern.md`): a plain exporter class with `static write(Builder $query, string $absolutePath): int` (League\Csv streaming with BOM, `columnLabels()`, `plainText()` formula-injection-safe, `jalaliDate()`/`jalaliDateTime()` helpers) paired with a queued `App\Jobs\Export{Report}` job (`ids`/`userId`/`locale` constructor, try/catch, success/error database notification), queued on the standard queue, never inside the request. Reference implementations: `ExportCalendarHits`, `ExportCalendarRules`, `ExportCustoms`, `ExportShipments`. The export applies the same filters as the screen, honors the same permission scoping (Report 7 reads no financial columns, so its export never selects them), and includes the flag/reason columns of the attention table. Do not introduce a new export library or pipeline.
- Production scale today is small (45 shipments, 13 customs, 60 purchase requests), so the risk is growth, not today's load; reports must still stay bounded by pagination and caching.
- Write-path cost already added: audit logging costs one extra SELECT + one INSERT per audited save; `activity_log` has no retention (never schedule `activitylog:clean` without `--log=calendar`).
- The invoice save writes header + rows in one transaction, and the stored totals (`total_net_weight`, `total_gross_weight`, `grand_total`) exist so reports never re-sum items.
